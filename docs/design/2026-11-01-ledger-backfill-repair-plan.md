## 1. 版本识别与分流：每版直接进入哪条路线

应用版本用于确定回归输入。实际分流以磁盘中的 schema、parser、组件 revision、manifest 和发布状态为准，不能仅凭安装包版本断言“已迁移完成”。同一用户可以同时具有下表多种状态。

术语：旧解析=compaction 修正前的已知 parser；新解析=当前 compaction-v1。Swift 与 Rust 的主 schema 数字只在各自实现内部解释。

| 来自版本 | Mac 主 schema / stage | Windows 主 schema / stage | 正式账处理路线 | 补全处理 |
|---|---|---|---|---|
| 0.9.0 | 6 / manifest1 | 9 / 无版本字段 v0 | L0：独立旧库一致快照后转换 | 旧 stage 只作旧证据；原文可用时建立新解析任务 |
| 0.9.1 | 6 / manifest1 | 9 / 无版本字段 v0 | L0；另保留这一版的聚合差异 | 同上；Windows 必须新增 v0 分类器，不能再因缺列直接 Fatal |
| 0.9.2 | 13 / manifest3 | 13 / manifest3 | L1；先解决候选迁移清单，再做13→14表示层转换 | 旧解析结果不能标为新解析完成 |
| 0.9.3 | 13 / manifest3 | 13 / manifest3 | L1；包括与后续14副本并存 | 同上 |
| 0.9.4 | 14 / manifest3 | 14 / manifest3 | L2；不重复进行13→14转换 | 仅缺少新解析证明且原文可用的来源补算 |
| 0.9.5 | 14 / manifest3 | 14 / manifest3 | L2；保留已发布投影、retained/floors、组件版本 | 同上 |
| 0.9.6 | 14 / manifest3 | 14 / manifest3 | L2；保留独立 Home/账户边界 | 同上 |
| 0.9.7 | 14 / manifest3 | 14 / manifest3 | L2；覆盖 support/cache 两份库及其 WAL | 同上 |
| 0.9.8 | A内14 / 旧解析 | A内14 / 旧解析 | C0：不再次归并完整 A；检查既有 ready 或中断 journal | 原文可用者补新解析，写固定池；缺失原文者保留旧账 |
| 0.9.9 | A内14 / 旧解析 | A内14 / 旧解析 | C0；尤其覆盖残留清单、部分导入和重复旧候选 | 同上，不要求先装0.9.10/11 |
| 0.9.10 | A内14 / 新解析 | A内14 / 新解析 | C1/C2/C3，按实际完成度选择 | 未开始则建立任务；已封存则核验接续；已发布则不重算 |
| 0.9.11 | A内14 / 新解析 | A内14 / 新解析 | 同0.9.10；优先覆盖本机数千 stage 的半完成状态 | 同上；不能再从零处理全部来源 |

尚存在已支持的中间 schema（如 Swift7/11/12、Rust10/11/12）时，按真实 schema 进入已有结构/会计/表示层步骤，不伪造对应 release 版本。未来或未知 schema 不降版本、不改标记，保留并隔离该分区；休眠旧 Home 不阻塞已支持的当前 Home。

### L0：早期独立库（Mac6/7、Windows9/10）

1. 冻结源 SQLite 含已提交 WAL 的一致快照，登记来源/格式/摘要；不直接复制裸主文件。
2. 在私有候选内执行已知结构→会计→表示层转换。重用已有迁移函数，拆开其中的结构转换与业务扫描入口，禁止通过初始化真实业务 owner 顺便扫描全部原文。
3. 旧数字和原始字段逐键保全；既有算法定义的会计修正必须留 legacy/retained/校正证明，不能为凑新结构把旧消费变0或丢掉无法细分的旧证据。
4. 结构转换不以原文存在为条件；需要原文才能证明的新语义在后台单独处理。缺失原文只限制文本关联或可证明的修正，不能删除旧账。
5. 候选核验通过才导入 A，源库和恢复材料不被提前删除。

### L1：独立 schema13

先按第3节确定哪份是可用已发布来源，再在私有快照中执行已知13→14表示层增补，保留 IDs、事件、原始指纹、retained、已有 canonical 状态。不能把“表不存在”和“表存在但有内容”都当空表处理；不以当前 JSONL 重建代替转换。

### L2：独立 schema14

不重复转换主 schema。只补实际缺少、已知支持的组件；随后按来源身份导入 A。原文是否存在不影响已有正式消费的导入。源数据已经导入且消费证明有效时登记/复用回执，不重新导入一遍。

### C0/C1/C2/C3：A 已经存在

- C0：旧解析，正式账先保持，生成缺少当前解析证明的来源任务。
- C1：新解析未开始，无合格 stage；只为所需来源建立任务。
- C2：新解析部分 sealed；复用合格旧 namespace/文件 stage，其余写固定池，不能先批量搬动所有 stage。
- C3：当前解析、正式发布证书和派生代关系一致；直接进入日常增量，不读完整历史原文、不重建全部聚合。
- A 内某个分区仍是已知旧 schema 时，只处理该分区：受控导出/快照→已知转换→核对→目标证明 CAS 后原子替换该分区；不能在总 A 上运行旧版文件 rename 迁移，也不能牵连其他分区。

## 2. 固定数据结构、操作状态和所有权

A 内新增一个固定暂存池 namespace，逻辑目录位于保留的 shared-pool 目录，不能与 `staging/<某Home索引名>/<来源摘要>` 的旧 job 搜索路径重合。沿用容器已认识的合法 stage 模块类别，登记、建表和池版本在同一事务完成；不增加未知根表。

池内固定六表，索引/约束在首建时一次建立：

| 表 | 作用 | 关键约束 |
|---|---|---|
| operations | 结构归并、补全、清理的持久操作 journal | op_id；owner；输入摘要；基准发布代；状态；失败原因 |
| jobs | 单来源任务头、原文证明、封存信息 | job_id唯一；owner、parser、codec、格式、行数/摘要不可冒名替换 |
| event_rows | 待导入数值事件 | job_id＋ordinal；仅数值/定位字段，无聊天正文 |
| fingerprints | 该任务的去重证明 | job_id＋fingerprint；保持重复事件的既有语义 |
| chunks | 来源分块连续性证明 | job_id＋chunk_index；字节数＋摘要 |
| publication_receipts | 已消费任务与正式发布代的绑定 | owner＋job_id唯一；绑定内容摘要、parser、epoch/generation |

事件 payload 使用有版本的无损行编码：保留 INTEGER、REAL 原始位、TEXT、BLOB、NULL及字段布局/时间单位，不能经 JS 浮点或本地时间字符串中转。两端共用池 schema 和语义 fixture；codec/字段布局显式区分，不能隐式把 Swift 秒与 Rust 纳秒互转。

暂存池 schema 版本、原 parser revision、正式账 schema 是三种独立标记。新增存储不得通过把旧 parser receipt 改成新值来“完成”任务。

## 3. 旧 schema-11 清单/候选/回滚：按阶段处理

此表适用于旧独立库恢复材料，不直接在活跃 A 上执行文件交换。先校验清单版本、规范同目录路径、所有权、源证明与 WAL；对未知路径、符号链接、孤立候选不得覆盖或删除。`retiring`是Mac曾发出的兼容阶段；Rust只接受其实际已知的phase枚举，不因表中列出某字符串就放宽未知phase解析。

| 旧阶段 | 证据与采用来源 | R 的动作 | 再次中断后的入口 |
|---|---|---|---|
| 无清单、只有正常主库 | 主库是受支持格式 | SQLite快照后走L0/L1/L2 | 复用同摘要快照 |
| prepared | 主库与source receipt匹配 | 复用完整副本；不完整则重做本操作副本 | prepared，源库不变 |
| copied | 已有匹配源的完整快照 | 在私有候选完成剩余DDL/组件转换 | copied或已持久化下一状态 |
| migrated | 候选转换已完成 | 逐字段/关系校验，核对源仍匹配 | 不重复转换已经完成的结构 |
| validated | 候选与旧发布事实有完整转换证明 | 作为受验证导入候选，不要求再在原目录搬库一次 | 导入前仍不算已发布A |
| switching | 可能正处于主库已移走的rename窗口 | 主库存在先验证主库；缺失时只在证明这个窄窗口、rollback符合原receipt及sidecar规则时采用rollback快照 | journal记录实际选用证据，不猜candidate为正式源 |
| switched | 可能已有后续正常写入 | 主库存在采用其当前提交状态；主库缺失不能自动以旧rollback冒充最新账；已被A消费则使用A | 不再从头执行旧切换 |
| retiring | 旧清理尚未完成 | 核对主库或A消费证明；转为受管保留，不继续猜删证据 | 保留终态回执 |
| retained | 旧迁移已完成 | 不再当成“迁移未完成”；A已消费则跳过旧输入 | 正常启动，无重复归并 |

Mac 与 Windows 对“已switched/retained却主库缺失”的处理统一为不复活较旧账。Mac 当前较宽的rollback回退分支应收紧到具有同等证明的rename窗口。已有A缺失但initialized还在时，同样不能拿过期旧库重建一个空/旧A冒充当前账。

真正缺少最后一份已发布事实时，程序保留现场并隔离其分区；不能靠新版本凭空恢复缺失数据。该边界不应扩大为其他已验证分区都无法打开。

## 4. 多旧库、维护推进、重复导入：明确选择规则

候选比较必须在同一 owner/Home/账户作用域内，优先于任何覆盖操作执行；不能凭文件名、文件mtime或总Token更大选赢家。

| 编号 | 发现状态 | 自动处理 | 禁止行为 |
|---|---|---|---|
| D01 | 同一分区两份逻辑内容等价，物理字节/WAL不同 | SQLite一致快照、逻辑证明后只采用一次，登记两份来源 | 按文件字节不同报冲突，或把两份相加 |
| D02 | 已知schema13/14两份 | 在私有快照归一化表示层，运行既有typed覆盖比较 | 跳过非空representation、retained或未知字段 |
| D03 | 较新候选严格保留旧事实并合法追加 | 原子选择经证明较完整的候选，保留两份原始材料 | 用较旧候选覆盖新独有数据 |
| D04 | 额度观察追加、policy3维护时间推进 | 仅复用既有精确特例：旧观察/claims/键/类型全部保留，有限合法时钟推进 | 忽略所有时间字段或任意数值变化 |
| D05 | Exact已知raw generation/位置/指纹修复推进 | 运行既有连续性/唯一指纹/已发布canonical比较；available=0不恢复为可用 | 用数值相同猜位置、重开不存在原文、跨Home匹配 |
| D06 | A正常运行推进后，又发现与最初导入来源摘要相同的旧副本 | 同owner、module、逻辑身份、非retired导入receipt匹配时登记alias/consumed，不重新覆盖A | 要求当前A字节等于最初快照；因compaction推进误拒绝旧alias |
| D07 | 同一UUID但不同Home/账户 | 保持独立分区，各自入账 | 跨账户按UUID合并 |
| D08 | 两份确实存在不可证明的数值冲突 | 两份都保留；已有可信A继续展示且不覆盖；无可信基线时只暂停该分区精确写入 | 取MAX、取mtime最新或自动SUM来消除错误 |

D06的alias登记也必须冻结/复核来源证明，在A事务内确认目标未被替换；另一分区的相同摘要不能充当所有权证明。alias不为D03/D05提供跨候选的覆盖许可。

## 5. 已有A的全局 importing：按状态恢复，不改一个字符串放行

`container可用性`与`operation状态`分开；迟到导入不再把已有ready容器全局改成importing。沿用既有根合同，不增加旧容器不认识的全局state值。

| 编号 | 磁盘状态 | 启动行为 | 允许写入 |
|---|---|---|---|
| I00 | 全新，无旧账、无A、无initialized | 正规初始化A/B及必要模块 | 建库完成后各自启动 |
| I01 | ready A、合法initialized、分区证明一致 | 先进入正常runtime，后台发现迟到旧输入 | 已验证分区正常写 |
| I02 | 已有发布代＋importing，pending仅涉及新分区 | 恢复旧分区可用；待导入任务后台继续 | 新分区通过校验前不启动writer |
| I03 | importing，pending涉及已有分区 | 核对该分区的已提交导入、模块发布状态与baseline；有完整证明才激活；其他分区不受牵连 | 禁止覆盖其独有新账 |
| I04 | 无initialized，但某些分区有已提交证明 | 核对首次迁移输入清单与这些分区的完整性；全部必要证明齐全才完成首次激活 | 不以孤立ready行冒充首次全迁移完成 |
| I05 | 首次导入中断，有原始/快照/候选/journal | 从最后已验证阶段恢复；未完成前显示恢复状态/已有可信快照 | 不启动未准备好的旧/新writer |
| I06 | importing但旧journal缺字段或只有path | 走已有v1 journal适配及分区级证据重建；来源路径只用于定位，不作为完整性证明 | 证明不足的任务保留、暂停；不全局无条件放行 |
| I07 | initialized存在，但A缺失或容器根合同/所有权不可信 | 保留所有材料，停止A相关写入，说明具体原因 | 不自动创建空A、不复活过期旧库 |

原始导入receipt证明来源曾被成功消费，不要求A在正常运行后一直与原始快照逐字节相等。重启时也不再逐页重验所有休眠分区或重新导入全部历史。对正在恢复的目标分区做必要核验，后台独立执行有界存储维护。

## 6. 旧暂存识别与新解析任务：不能混用完成条件

| 编号 | artifact状态 | 识别/处理 | 能否直接满足R的新解析任务 |
|---|---|---|---|
| S00 | Windows0.9.0/1，无manifest版本字段 | 新增v0 reader：精确已知四表/列布局、单manifest、已知parser/migration、owner/path/session；完整行需quick_check/标志/字节/计数证明 | 不能；保留隔离后从可用原文建立新任务 |
| S01 | Swift早期manifest1/2或两端旧parser manifest3 | 读取已支持字段；源签名变化属于旧结果失效，不当成未知格式 | 不能冒充compaction-v1完成；保留旧证据，再补当前规则 |
| S02 | 0.9.10/11当前parser，complete=1且所有证明匹配 | 复用原文件/namespace，经统一artifact接口读取 | 能，仍须最终来源复核；Windows还要核对building/base代 |
| S03 | 已知格式complete=0或building | 不计入正式账；保留可核对的任务头；重新处理当前未封存文件 | 不能；本次保证sealed级断点，不承诺半文件恢复 |
| S04 | 目标parser相同但源文件已变/基准不再满足 | 保留旧artifact为superseded，重新规划该来源 | 不能凭旧job ID硬复用 |
| S05 | source在本轮中消失 | 撤销该轮未提交部分，重新发现；缺失源的旧发布消费保留，artifact留证 | 不能用sealed标志替代来源证明 |
| S06 | 已有正式publication receipt | 同owner/job/digest确认已消费；只做清理 | 不再次导入，即使payload还在 |
| S07 | manifest未来版本、列集/identity未知、seal损坏 | 不删、不降版本、不强行套v0；隔离本任务及相关分区发布，已验证旧账仍可展示 | 不能 |

v0的已知完整性标志是`sqlite-quick-check-v1`；complete=0的标志为空、actual_bytes=0也可能是合法中断状态。缺少manifest行时没有parser/owner证据，不把空壳自动归成已知v0。版本只用来识别格式，不能由R替它补出旧版本没有保存的source/base generation证明。

缺失原文者：长期保留已发布消费；不存在的模型、时间、原文位置或compaction新增成本不能猜补，未知只影响相关字段/区间，不把整库统计清空。

## 7. 新任务完整生命周期与原子边界

| 阶段 | 做什么 | 持久写入 | 此时崩溃怎么处理 |
|---|---|---|---|
| P0 只读盘点 | 进程锁、路径、A/B合同、旧来源、journal、阶段分类 | 不修改旧库 | 下次重复盘点，无副作用 |
| P1 建恢复计划 | owner隔离，选L/C/I/D/S路线，固定输入摘要和基准 | 只登记本操作；新增操作不能污染已有ready | 按同op和相同输入接续；输入变了另建attempt |
| P2 快照/转换 | SQLite含WAL快照；旧schema只在候选转换 | 受管快照、转换候选、proof | 校验后复用；同摘要不反复生成全套备份 |
| P3 正式旧账激活 | 来源选择、保护字段/关系核对、目标proof CAS、导入 | 初次A/单分区原子导入 | 未提交仍是旧态；已提交有receipt，不重复导入 |
| P4 构建补全 | 全局规划任务，优先复用S02，剩余解析进TEMP/有界缓冲，写固定池 | 只写building/sealed任务，不改变正式公开账 | sealed复用；building只重做这一文件 |
| P5 正式发布 | 最后复核源证明、事件/指纹/归因/聚合/扫描证书，写消费回执 | 见下方两端边界 | 成功或旧完整代；无部分正式账可见 |
| P6 发布后清理 | 按owner/job/receipt清理payload、旧stage对象 | 已消费payload和受管临时对象 | 可重复，失败不撤销已提交账、不阻塞启动 |
| P7 日常增量 | 原检查点后缀读取；无变化不补历史、不重建聚合 | 已有增量流程 | 普通恢复，不重走整个升级 |

Swift：保留整轮外层事务与内部savepoint。正式事件、canonical、聚合、epoch/generation、扫描证书及任务消费回执同事务提交。

Windows：沿用已存在的building/pending层；逐文件可持久化pending，但普通读者只读published。最终事务发布pending、更新published_generation/证书并记录消费回执。不能提前清理仍被pending恢复引用的stage。

消费唯一键是`owner＋job ID`，绑定不可变摘要和正式发布代；同键同摘要已消费则幂等跳过，不同摘要拒绝。旧artifact以原分区身份＋artifact_id建立稳定映射。正式事件既有去重仍保留，不能只依赖job回执去重。

## 8. 连接、锁、进度与磁盘：具体运行规则

### 连接和DDL

- 容器/池结构只在初始化或明确结构转换时变化；每个补全job不得创建MAIN对象。
- 使用受控连接和已有序列化writer协调：worker最多4；同一handle仅串行使用；解析不持有A写事务。
- byteCount、seal、observation使用所属任务/读事务的已有连接；legacy reader在已验证的namespace内读，不逐job重新安装/枚举全库目录。
- 本轮目录读取一次并按内部登记/隔离/删除更新；来源/容器变化、重启使相关缓存失效，不能永久缓存绕过证明。
- 不共享可变businessBinding跨线程，不把sealed的只读状态意外带进writer；所有ownership/容器身份检查保留。
- 正式发布事务不为了让锁更短而拆成可见半成品；单独记录其峰值写锁/WAL，实际过慢必须在本版解决后才能放行。

### 进度

分开显示“计划来源数、已复用、已封存、核验、提交、清理”。按job ID累计，跨四任务批次不归零；重启从持久记录恢复。一次任务只计一次，来源改变时明确重计划。没有完成正式发布时不显示100%升级成功。

进度最多每250ms向主线程发布一次；schema/proof/目录工作不在主线程执行。显示最后推进时间、暂停原因，不编造剩余分钟数。

### 空间与重试

空间预算=尚需创建的原始快照＋转换候选＋A新增页估计＋最终提交WAL估计＋512MiB保留余量；快照按SQLite一致视图页面数估计，并按实际写入逐批修正。固定表不等于暂存数据被限制在四任务大小。

低空间：停止派发、释放事务，保留旧账与sealed任务。只在用户重试或低频空间重检确认恢复后继续，不高频空转、不清旧账腾空间。

锁忙：只重试当前数据库步骤，带退避和次数上限；不因此重新解析全部历史。来源变化：只废止对应未发布计划，重新核对该来源；连续变化时暂停该轮，下一正常刷新重试，不无限全量循环。

## 9. 快照、旧库与清理：哪些删、哪些绝不按名称删

| 对象 | 本次规则 |
|---|---|
| 用户Codex/Claude会话、配置、账号凭据、其他软件数据库 | 不删除、不移动 |
| 正式A/B和其中已发布历史 | 不作为清理对象；不能清库重建 |
| 已消费新pool payload | receipt与发布代一致后可清；保留小型防重复回执 |
| 已消费旧stage namespace | 必须证明job已发布且无pending引用；先留消费/retired证据，再按精确对象集合分批DROP |
| 未发布sealed/未知stage | 保留，按S表处理；不能为了减表数批量清空 |
| 已知building临时内容 | 只有确认本程序所有、从未发布且已有可恢复来源时才可回收；原文缺失时先保留证据 |
| 同一输入的重复归并attempt | 以owner＋源摘要＋转换合同复用；不能每次重试都造一份original和normalized |
| 原始迁移备份、574个看似不活跃的分区、其他历史副本 | 本次不推测删除；有证明的临时冗余可回收，最后一份历史证据保留 |

旧stage清理复用连接、按时间/对象数预算分批；DDL导致的读缓存失效也在后台处理。清理不是启动关卡。无需立即缩小A的物理文件，不在启动前跑全库VACUUM；空闲页留给后续复用，沿用有界维护。

约1.55万张非stage表的处理决策是保留，不把“它们看起来空”当成可删依据。通过固定连接、一次登记读取、无job级DDL消除已定位的反复开销；把这一基数保留在性能门禁中，不能先删掉它再宣布提速。

## 10. B库、路径和设置的同步兼容

B不迁移本次正式账：不存在则按现有各模块owner初始化；已存在用量表但尚无测速表是已知首次初始化状态，模块只增补自己的结构，不重建整个B。已有B必须保留canary、用量、速度记录、上报队列和用户配置。

Windows的长路径规范化只发生在实际文件I/O边界，保持旧receipt/source identity原字符串；正常路径与verbatim路径比较一致，覆盖超过260字符的本程序备份路径。

不重置开关、模型色、客户端启用、上报授权或统计目录。后台恢复不会替用户开启上报/Claude网络额度功能。事件名listen修复若尚在独立PR中，只核对并集成它，不重复写一套；该错误未解决不能成为可发布候选。

## 11. 失败后用户能看到什么、程序能做什么

| 失败 | 保留和展示 | 恢复动作 |
|---|---|---|
| 追加导入低空间/锁忙 | 已验证旧账可用，相关操作暂停 | 从该操作最后验证阶段继续 |
| 一个Home补全失败 | 该Home旧完整代及更新时间保留；其他分区继续 | 不发布本轮半成品，保留stage再试 |

### 本轮补查的三条具体链路

额度历史：Mac peer已有缺cycle列的读取适配，但Rust peer查询仍硬引用四列；Rust生产分支传播错误，测试分支却吞成空数组。Rust peer还仅接受source=swift，不能据此过滤已经迁入的旧Tauri事实。修复须保留账户/套餐/limit/home范围约束、去重与安全legacy桥接，不能直接无条件混入所有来源。

checkpoint/stage：现有追加校验失败会改走full rebuild；完整stage若对应旧边界或旧base，复用校验失败，又不属于已知可重开分类，会在路径固定的primary stage处Fatal。S04必须覆盖这条完整状态转移，保留旧证据后使用新job，不通过改哈希/删checkpoint来掩盖问题。现场旧哈希最初由哪个版本写入仍未确认，必须单列调查结果，不能把“发现阻塞链”写成“已确定哈希成因”。

外部实时库：Rust生产open_read_only_index错误统一进入open_exact_business_store；state_5的active rollout/线程元数据调用点也使用它，已有消费回执可使后续读取固定在首次导入的A副本。测试分支却直读原文件。必须分离“本程序账本读者”和“外部实时只读读者”，逐调用点分类，禁止按任意路径套用旧库迁移。Mac当前StateRefreshSnapshot从外部WAL只读刷新；两端应共享这一语义，不复制错误路由。

以上为代码核查所得，尚未实施产品修复或运行T33–T37；它们与原有万表性能/累计进度问题分别验收。

### 数据正确性门禁

逐来源/主键比对时间、原始模型、所有Token组件、accounting分类、reported/legacy字段、指纹、source/chunk、retained/floors、canonical关系和发布证明。不能只比较总Token或行数。只有既有已定义规则的修正允许差异，且原值和修正映射完整留存；不得因原文缺失减少已入账历史。

测试使用完整性/关系检查和每个phase的业务不变量；quick_check=ok不代表业务账正确。云端仅用合成/脱敏输入，Home/cache/AppSupport必须隔离并有fixture所有权标记，不上传真实账本或对话，不删除非测试自建目录。

### 性能门禁

在T29同样的万表基数上，正常已就绪启动不等待全历史补全/清理；给定云端runner的已就绪数据可用时间目标≤3秒，主线程无数据库重活。首次结构迁移单独计时，不能与warm ready混为一谈。

大schema稳态seal/header元数据查询P95<10ms；正式补全全流程记录解析、数据库管理、最终发布、恢复、清理各自耗时，以及CPU/RSS/写锁/WAL/空间。新旧版本同等数据、验证强度、runner比较；旧版超时如实记，不以不同任务数计算提速。
