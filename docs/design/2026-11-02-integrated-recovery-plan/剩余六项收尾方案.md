# 剩余六项收尾方案

日期：2026-11-03。本文件补充既有完整方案与C05/C06/C07，不重开一套迁移设计。产品实现基线为40163c48；本文件是方案，不表示六项已实现或验收通过。

长事务结构调整仍待用户评审。用户目前要求解释与完整方案，不视为批准切换。独立分支内继续既有正确性修补和自动测试；不合并main，不安装、替换或重启正式应用，不签名、不发布，不向Anthropic发请求。

## 1. 已有基线和明确失败

- 最新40163c48[常规Swift/Rust/前端检查](https://github.com/hututuo/codex-token-bar/actions/runs/41563902354)、[真实0.9.7双端升级](https://github.com/hututuo/codex-token-bar/actions/runs/41563902287)、[0.9.8～0.9.11双端8条形成状态升级](https://github.com/hututuo/codex-token-bar/actions/runs/41564153315)均已通过。后者覆盖完整／中断状态及恢复后三次独立重启。
- 上述常规检查没有执行50万事件压力，也未启用Windows诊断开销profile，不能覆盖下面的失败。
- 最近完整压力来自cb227a48，[原始运行](https://github.com/hututuo/codex-token-bar/actions/runs/41557967635)：503128事件、4124来源和25000旧对象保留。Swift最长写锁284.589秒、补全450.662秒、无变化P95 1.839秒；Rust/Mac补全737.853秒、P95 1.237秒；Rust/Windows补全1093.275秒、P95 2.883秒。原始事件身份／类型／数值对账一致，MAIN对象及store增量为0。
- 同轮Windows诊断profile为6.413%开销，预算5%；每模式7组交错样本，512KiB payload，实际导入结果和原文件保持。此轮只确认预算失败，未证明唯一性能原因，不能直接归因于某一次fsync。
- 40163c48已减少Rust验证／导入间的一次重复快照还原；尚未用同规模profile证明性能已达标。

## 2. 不变边界

1. A、B仍为两个长期业务库；不清库重扫，不整体替换A，不新增长期测速／迁移库。
2. 旧账包含原始会话已经删除的消费；以账本事实及可验证绑定材料恢复，不要求用户找回原文。
3. 原UsageEventLedger.admit、correction、compaction、去重、canonical、费用和周期算法继续使用，不能另写简化记账分支。
4. 正式发布保持整轮原子性。账目、投影、checkpoint、generation和消费回执一起提交，不公开半轮结果。
5. 已发布旧代在后台补全期间保持可读；低空间、日志失败、清理失败不得撤销已完成发布。
6. 原预算、规模和负面测试保留。没有最终通过证据不封候选。

## 3. 执行顺序与每项退出条件

### 第一步：解决Swift整批发布长写锁

结构沿用[长事务补充评审](长事务补充评审.md)第3节，先影子验证，再切换实际提交。

1. 保留同一Exact owner串行调度。在A的受控只读快照中固定本轮相关分区的基准，流式送入用完释放的私有SQLite工作区；不切全局路由、不注册业务store、不复制其他owner和B。
2. 在工作区调用原记账／投影算法，得到完整变更计划。所有连接必须显式指向工作区；禁止捕获正式driver回写A，也不能提前消费实际pool任务。
3. 第一阶段只计算并比较：与原路径逐表、逐稳定ID核对类型／值、binding、turn、未决、correction、canonical、费用及归因。必须证明影子计算没有A副作用；此时仍不接替实际发布。
4. 比较通过后，接最终提交：申请A写锁，以有索引的集合查询核对相关基准、owner、合同、stage seal及来源边界，再批量应用差异，并同事务记消费回执。不能只比较mtime、总和或一个未覆盖所有写路径的generation；不能用临时副本覆盖A。
5. 基准变化就放弃本次计划、保留已sealed任务，走现有有上限协调重试；不丢期间新账，不每次重新解析全部来源。临时工作区不是重启所依赖的第三份权威材料。

退出条件：原路径与计划结果一致；准备中断／计算后新增账／来源改写／CAS不匹配／提交中断／提交后重启均保账且幂等；50万事件最终写锁≤10秒，进度空窗≤30秒。不能只让UI计时器继续转来代替释放锁。

失败退路：本步骤按影子、CAS、实际批量提交三个提交分别保存。未达到结果等价性时不启用新发布；保留现有旧代和恢复任务，不通过降级运行旧writer来回退。

### 第二步：解决Rust大批补全超时

1. 固定Windows与Mac runner上相同输入，分别测目录准备、基准快照、比较、验证、挂载、导入、聚合、提交及恢复。准备耗时与补全耗时可能重叠，按实际嵌套区间解释，不直接相加。
2. 保留401的同一已验证私有快照复用；进一步减少profile证实的同一job内重复还原、目录加载与逐行SQL往返。复用必须绑定job／owner／合同／seal，不跨尝试信任旧快照、不省略完整验证。
3. Windows沿用现有持久pending及最终原子提交。先优化实际热点；只有测出剩余最终事务同样超标，才按同一已评审发布合同调整实现，不重写已正确的账务算法。两端统一结果／证明／恢复规则，平台文件占用处理各自测试。

退出条件：4124来源及50万压力各自按原门禁完成，补全≤600秒；公开总耗时、最大写锁、WAL及内存。账目身份／类型／数值一致，新job不新增MAIN表或store。

### 第三步：把日常刷新压回预算

1. 单独测无变化、单源追加、新会话、同尺寸改写、来源删除、重启后第一次刷新；不能只测历史补全后的热缓存。
2. 对源目录枚举、来源状态查询、schema／授权加载、proof及summary分别计时。消除确认的重复加载，批量取得相关来源状态和pending集合，复用已验证owner连接与编译语句，避免每轮重装大目录。
3. 派生缓存必须有覆盖相应写路径的事实版本和明确失效条件；schema_version仅能控制结构缓存，不能当内容版本。mtime／size不能代替原有内容、物理文件与前缀保护。
4. 正常追加继续只解析新增部分；未变化来源不重解析、不创建attempt或备份。后续有任何异常只重检受影响来源，不冻结其他已知模块。

退出条件：原受控大库至少20次无变化刷新P95≤1秒；parser调用0、新attempt／备份0、可信事实不变。追加／改写／WAL变化必须仍被识别，不能靠返回陈旧缓存过关。

### 第四步：降低Windows诊断开销

1. 先分别测诊断初始化、所有权标记、事件序列化、刷盘与close，区分固定成本和每源成本；不先猜是fsync，也不把一次波动当作已修好。
2. 详细事件保持有界批量，避免每来源开关文件／重做目录检查／重复序列化；保留明确的关键持久化点。权威操作状态仍由SQLite事务和回执保障。
3. 保留原7组交错样本、512KiB输入及5%门槛。增加冷／热和重复运行用于解释波动，全部保留，不丢掉失败轮只挑绿灯。最终检查显式开启profile，普通CI绿灯不代替它。

退出条件：双端诊断开／关／写失败／目录未知状态下账务结果一致；启用诊断耗时增幅≤5%；日志仍受30天／50MiB上限约束，关键失败不被轮换丢失。

### 第五步：完成旧库和重复备份安全收纳

1. 只对程序已登记材料建立清单：旧独立库、original／normalized、schema11 candidate／rollback／manifest及stage。路径、owner、完整内容证明、转换合同、发布回执、未完成操作引用分别记录；不扫描用户任意目录按名字猜归属。
2. 现有retired只证明A内材料被消费，不等于磁盘文件可删。source_digest也不能一律当字节SHA使用；schema11缺完整证明时，先以旧格式只读适配核验，无法闭合证明就保留。
3. 已完整导入且无后续变化的旧输入先退出自动发现。所有恢复依赖必须仍指向一个验证过的保留副本，保留至少一份有效升级前快照，绝不删除最后一份证据。
4. 证明全部成立的冗余材料先移入受管隔离，记录原位置、完整摘要、去向和状态，再进入后续回收；不新增永久全库副本。动作前复核文件身份、占用和引用；WAL/SHM按一致家族处理，符号链接、文件被替换、未知材料一律停止。Windows须验证句柄关闭及重命名行为。
5. 清理中断可接续，重复清理幂等；隔离或回收失败只记维护状态，不影响正常启动或已发布账目。用户导出、客户端原始日志／state及无所有权证明文件不碰。

退出条件：旧版形成材料与未知文件混放、原文缺失、pending引用、文件替换、清理中强退、Windows句柄占用均有反例；误删为0、重复材料不再进入导入、恢复所需材料保留。本阶段只在一次性测试副本执行，不操作用户正式数据。

### 第六步：补齐后台资源与唤醒验证

1. 比较前台、隐藏、重新显示、休眠／唤醒、快速切换来源、重复订阅／卸载，记录CPU时间、I/O字节、扫描次数、子进程数、监听数、内存和UI长任务。无机器能耗计量时只报告资源代理，不称为实际功耗。
2. 隐藏窗口暂停无用重绘、演示动画和重复派生；必要账本采集保留。一个来源一个owner，同源并发合并，唤醒触发必要核对而非多轮同时全扫。
3. 重试沿用既有上限，低空间／锁忙不每秒重启扫描或子进程；额度重置、回弹等权威观察不得因窗口隐藏丢失。

退出条件：无遗留监听、扫描／唤醒风暴或隐藏动画计时器；不出现扫描／JSON比较占主线程的100ms级长任务。自动探针与生产入口分别说明，探针不能覆盖的机器能耗明确未测。

## 4. 最终组合验收

1. 六项以可独立回滚的源码／测试提交推进；每项先局部验证，再云端对应生产路径，不把文档或模块probe算整机验收。
2. 固定同一个最终源码SHA运行Swift、Rust、TS、UI、双端非cfg(test)生产存储入口及完整压力；不拿前一个提交的绿灯给后一个提交背书。
3. 原0.9.7、0.9.8、0.9.9、0.9.10、0.9.11双端形成材料保留，覆盖完整启动、中断恢复、恢复后三次独立重启及无新增attempt／备份；保留PR7 16项与V01～V20映射。
4. 包括原文已删除的旧账、目标独有新账、合法correction、compaction未知量、canonical继承／镜像，以及图表最后一格的费用和气泡一致性。不以费用总和相等代替逐事实保全。
5. 任一账目变化无法解释、恢复失败或主要性能超标，保留输入／profile并继续修，不封候选、不放宽预算。

完成交付是分支源码、同SHA报告及待后续验证的候选源身份；不自动安装、签名、发布。长事务结构如未获评审确认，仍仅继续原合同内小修和测试，不提前实施第一个步骤的结构切换。
