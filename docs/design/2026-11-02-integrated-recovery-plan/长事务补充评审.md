## 3. 推荐结构：锁外准备，锁内核对并批量应用

### 3.1 准备完整发布计划

Mac保留一次Exact owner同步锁，在A的短只读快照中固定该Exact分区的基准，而不是持A写锁做逐行核对。

使用SQLite自动清除的私有工作区保存该分区所需的基准和计划。它不注册为业务store，不切换全局route，不接替A，不复制其他owner／B，也不是新的历史账本。读取和写入流式分批，沿用typed-row合同，不用JSON或Double改写整数。

复用现有 `UsageEventLedger.admit`、身份关联、correction、turn、canonical、聚合、checkpoint和generation计算，在私有工作区得到本轮完整的预期变化。实际parser继续只在来源需要时运行；已sealed任务继续复用。不得创建“模型补全另一套记账算法”来只让压力夹具过关。

准备阶段必须明确隔离副作用：

1. 所有计划DDL／DML只能使用私有连接；禁止通过捕获的driver或全局route回写A。
2. 消费回执、任务清理和对外发布延后到真实A提交后；计划不能消费实际pool任务。
3. 计划只存所需原始结构、旧值及变更；没有完整基准或无法支持的旧合同就停止该计划，继续显示原发布代。
4. 大字段继续有界；不能把整源或整账读入数组。空间预算含私有计划、池、WAL和512MiB余量；不足时暂停操作，不让可信旧账失去可读性。

### 3.2 写锁内重新核对

计划完成后才申请A writer。最终事务必须核对：

| 对象 | 核对内容 |
|---|---|
| 容器与owner | 文件身份、已验证route、owner读写权限、原schema／codec合同 |
| 事实基准 | 相关实体全部旧值与类型、主键集合／行数、来源和稳定ID、binding、identity、turn、序列、correction与retention |
| 发布基准 | provenance、generation、canonical排除关系和聚合基准；不能只比较墙钟或mtime |
| stage | job／owner／contract／artifact、seal／payload摘要；恢复材料不因计划存在而降级校验 |
| 来源边界 | 保留现有已验证前缀、追加／重写／截断／替换保护；变更不能绕过原判据 |

不能把 `data_version`当跨连接持久版本，也不能假设一个现有generation字段覆盖所有写路径。现有版本标识不足时，必须用成组旧值／类型／主键集合比较补足CAS；相关事实改变则放弃本次计划并重新协调。其他无关owner的正常提交不应迫使Exact从头重解析。

成组核对用有索引的SQLite集合查询，禁止把原来百万次Swift往返换个名称再放回写锁。整数、NULL、原始TEXT/BLOB和REAL类型边界与既有typed proof一致；不能用舍入、总和相等或有损拼接代替逐事实核对。纯SQL不能证明的形态必须单独处理并测试，不能默认为匹配。

### 3.3 同一次事务应用

- 将验证后的变更批量写入实际Exact实体、canonical、聚合、checkpoint与发布代。
- 真实pool消费回执和本轮完整发布同A事务提交；不存在“事实先成功，回执以后补”。
- 不用旧私有副本整体覆盖A，不删除A独有新账，不提前公开四来源或半轮结果。
- 任何步骤失败回滚A，原代与sealed任务保留；成功后才释放旧展示快照、报告100%并排队受管清理。
- 进程中断时私有工作区可丢弃；重启由现有operation／pool／receipt接续。它不能成为用户必须手动修理的第三份权威材料。

Windows保持已存在的durable pending／最终原子发布边界，先落实已定位的重复还原优化及无变化profile。是否需要同样的计划化改造由其实际剩余相位决定，不因为Mac需要就重写Windows已正确的算法；两端结果与证明合同统一。

## 4. 不采用的替代

| 替代 | 不采用原因 |
|---|---|
| 写锁预算改成300秒，或删4124／50万档 | 未解决其他A writer被阻塞，违反既定门禁 |
| 每四来源提交一次并立即公开 | 改坏整轮发布及跨源canonical／归因合同 |
| 只靠进度心跳或修改提示文案 | 只能减少静默，不释放writer |
| 再开一个长期Exact库或另建队列库 | 新增权威来源／迁移负担，违反A/B限制 |
| 只加纯模型快捷记账分支 | 压力夹具可能变快，但实际correction／compaction／旧绑定仍保留第二条长事务，增加双算法维护成本 |
| 缓存上轮查询结果并跳过CAS | 可能覆盖期间新增消费，不能接受 |

## 5. 实施与退出门禁

1. 先将当前正确性修复独立提交，旧测试和旧版产库基线固定；不安装正式版。
2. 增加完整计划与原路径的对照：相同输入得到同样的稳定ID、每列类型／值、turn、binding、unresolved、correction、canonical、费用及归因。保留合法数值修正，不将其误认丢账。
3. 先实现只准备、不发布的影子比对；确认没有A副作用和缺失语义后，才接最终CAS与批量应用。不能把影子比较成功叫作修复完成。
4. 注入准备中断、计划后追加／替换、期间目标新增账、identity冲突、CAS不匹配、应用中途强退、回执提交前后强退、低空间、未知合同；验证旧代／新代完整性与跨重启幂等。
5. 保持13／128／512／4124／503128事件与旧25000对象输入，实际测写锁、总时间、空窗、无变化P95、WAL和内存。10s／30s／600s／1s及5%预算不自行改动。
6. 最终同SHA跑Swift／Rust／UI／TS、真实旧版升级、完整启动、恢复和三次重启；未过门禁不封候选。

物理旧库／重复备份／schema11 rollback收纳仍是独立未完成项。现有消费回执不自动证明物理文件可删；没有完整内容及恢复引用证明的材料继续保留。该问题不能以性能发布计划为由顺手删除。
