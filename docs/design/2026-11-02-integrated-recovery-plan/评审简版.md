# 整体修复方案 · 简版

状态：修复方向已获同意；本轮补齐执行文档，压缩后实施。未改产品代码、未合并、未替换或发布。[详细技术方案](完整方案.md)包含16项取舍、版本/状态恢复、数据结构、退出条件与验收；[执行清单](执行清单.md)规定逐阶段动作，[接续入口](压缩后接续.md)记录下一步。

## 已确定的七项

| 决策 | 推荐方案 | 用户看到的变化 |
|---|---|---|
| 数据库怎么修 | 保留A/B和全部旧账；A内建固定暂存池，任务存成行 | 不再每个文件长出四张表；不清库重扫、不整体搬库 |
| 启动和恢复 | 有可信旧账就先显示，恢复单独后台接续 | 一个来源出问题，不再让额度、速度、其他统计一起消失 |
| PR7怎么用 | 16项逐项采用或改造；结合PR6的兼容、进度和诊断 | 保留有效修复，避免两套冲突逻辑叠加 |
| 显示和统计 | 摘要／图表／额度／速度各有版本；费用选区共用一个快照 | 不再摘要到了图表却一直等，不再气泡和底部金额对不上 |
| 历史升级 | 自动识别0.9.7–0.9.11及已有中断状态，已完成工作复用 | 直接覆盖更新；不用清库、删清单或依次安装几个版本 |
| 性能与诊断 | 固定连接、无job级建表、批量日志；双端跑4124源与大历史 | 修真实卡顿；不靠改进度字样或新增大量刷盘来掩盖 |
| 交付 | 一个整合修复版，数据／恢复／性能门禁全部过后再封候选 | 不再让用户安装一个版本只排除一个报错 |

## 对PR7不是全盘接受

**先固定PR7的16项修复作为回归基线，不为重构重写已正确的实现。** 后面的改动只针对有证据的缺陷、确定的合同冲突和性能问题；同输入比较及16项回归不通过，就撤回该增补或修正冲突，不删测试／放宽断言。F07/F08先保留已验证实现，补测试，不能只因为想换结构就重写。

- 保留：事件名、旧额度读取、SQL索引、Windows路径、权限、追加验证等有明确证据的修复。
- 改造：旧暂存的新任务改用固定池；实时state使用真正只读及可靠更新检测；统计改成独立版本，不绕过版本判断；渲染按事实版本去重。
- 补齐：PR6旧state列兼容、存储／监听异常、Mac累计进度；我原来查到的暂存表累计、反复开大库和ready账本被新增导入挡住的问题。
- PR6逐源同步刷盘改为有界批量日志。日志是排错工具，不成为新的卡顿源。

## 最重要的取舍

**旧账可信时继续可读，失败恢复只隔离受影响部分。** 真正损坏、归属冲突或无法证明的记录不会被猜成正确；已知金额和其他正常模块继续保留。

本次保持原界面、费用／速度／周期算法和上报开关，Claude继续只读本地。固定暂存池需要少量内部表与适配层，但不再做整个账本迁移。

## 这次就要收束

新任务只走固定池，旧stage只留恢复读取；普通只读与导入分开，启动与手动重试共用调度，PR6／7重叠部分只留一个正常实现。替换后留下的重复writer和临时开关本轮退出，不承诺以后再删。

以后仍可继续拆大文件、整理历史副本，但拆代码不连带再迁账；物理清理必须先证明所有权、已发布和可恢复。旧格式的读取兼容不能为了代码好看而删除。

## 完成标准

- 各旧版本直接升级、完整启动、中断恢复、重复启动，原账和新账都有对账证据。
- Mac和Windows都走正式存储入口；512／4124来源、大量旧表和50万事件全部测试，性能不过不发。
- 正式发布保持整轮一致，任务回执与账目同事务；坏任务、清理失败和日志失败不破坏旧账。
- PR7独立基线、各组增补、最终整合都作对照；原16项任何一项退回，候选不通过。
- 最后交付源码／测试／对账／性能报告；替换和发布等待后续指令。
