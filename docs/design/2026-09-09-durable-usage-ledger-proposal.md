# 历史用量保全与双格式兼容方案

状态更新（2026-09-09）：双端持久账本、旧索引升级、原文代际关联、增量、可追溯数值修正及应用数据目录搬迁已接入生产路径，测试与真实隔离副本验证见 [实施记录](../maintenance/2026-09-09-durable-usage-ledger-progress.md)。下文保留设计边界，具体已实现范围以实施记录为准。手动补差和应用/Windows 实机验收尚未完成；没有修改运行程序或用户活动库。

最新范围：用户已授权开始修改，并要求先落盘方案以便上下文压缩后按计划接续。停止历史追找、保留已有证据的约束仍然有效；兼容、旧账持续保全及后续自行手动补差进入实施范围。找回全部历史不作为实施前置条件，不自动填入任何补差值，也不将计划落盘宣称为功能已经上线。

## 1. 问题与目标

上游 legacy→paginated 转换可能裁掉部分子 Agent 早期原文，也会对部分保留记录重写外层时间和历史前缀标记。Bar 因此不能继续假设“原文件随时可以重建全部历史”。兼容需要同时覆盖原文格式、旧索引结构、会计字段、来源身份与详情读取。

目标：已有证据不因源文件改写/消失而静默丢弃；一笔消费在累计、周期、模型和任务统计中采用相同入账判定；日常仍只读新增后缀。保存足够的数值明细，不复制聊天全文。历史缺项保持缺项，不能把累计种子当成一轮消费。

### 1.1 哪些情况会丢什么

| 情况 | 原文/索引实际影响 | 新方案应保住什么 |
| --- | --- | --- |
| 普通的模型上下文压缩 | 出现 compacted 本身不证明旧 JSONL 已删 | 不因看到压缩标记就排除之前的真实调用 |
| 上游分页迁移的子 Agent 安全截短分支 | 可能不再写入较早消息、工具结果和逐次用量；恢复上下文及较晚记录仍在。子任务判定必须同时支持 source 的 SubAgent 形态及 thread_source=subagent | 原文省略的历史消费从已有旧账保留；新旧重叠仅计一次 |
| 子 Agent 未满足安全截取条件、普通任务转换 | 回退/采用完整重放及规范化、回滚处理，不走上述子任务截短分支；仍可能变更格式与定位 | 兼容两种事件形态，旧位置失效后重新关联，不把格式差异当消费消失 |
| 迁移将子任务旧记录全部标为恢复前缀 | 文件里仍有真实记录，但常规历史展示不投影该前缀 | 区分父任务继承、子任务自身用量与展示前缀，不能整段当父任务用量排除 |
| 部分迁移重写外层时间及字节位置 | 旧记录还在，但可能错进日期/周期；旧 offset 可能指向别的内容 | 保留可信旧时间；正文定位绑定文件代际并验证 |
| Bar 用新原文重建后替换旧 events，或来源消失时级联删除 | 新原文没有的旧用量，原本可能还在旧索引里，也会被替换掉。此前缺少永久保全旧账是 Bar 的处理缺口 | 先保护旧账，替换/删来源只影响扫描与定位，不静默删除消费 |
| 原文件损坏、磁盘/权限异常、文件暂时找不到 | 不能完整读取，不等于真实消费为零 | 保留已发布账目，隔离对应来源并有界重试，不拖垮所有功能 |
| 原文和旧数值索引都不在，仅剩累计数或摘要 | 无法还原逐次时间、模型和组件组成；不存在可靠的全量精确恢复办法 | 不猜补；允许用户单独手动补差，明确其性质 |

7 月 24 日是现有旧索引备份的截止日期，不是丢失行为的日期边界。已核对到 8 月的子 Agent 同样只有较晚恢复上下文；具体损失比例不能用一个备份覆盖范围外推。

已保存的恢复证据：7 月 24 日 schema 2 旧库以及当前双端一致性快照；69 个子 Agent、12,744 条、2,101,884,661 Token 的强数值桥接候选已独立提取，仍未导入。它们是候选，不是新增自动补差，也不是已恢复到应用的用量。后续若导入，必须经过同一去重/保全流程，且不能与手动补差无提示地重复补偿。

## 3. 建议的存储边界

采用一个持久数据库内的逻辑分层，避免账本和扫描检查点跨库提交：账本是权威数据，扫描位置和聚合是缓存表。数据库移到各端正常的应用数据目录（macOS Application Support；Windows 对应应用数据目录），不再视为可随意清理的系统缓存。两端各自拥有数据库，使用一致契约和共用测试样本，不让两个进程直接共同写同一库。

### 长期保存

- 每次已观测用量：独立事件 ID、输入/缓存输入/输出/推理输出、原始 reported total、当前入账分类及算法版本；原始组件与修正结果分开。缓存输入包含在输入内，推理输出包含在输出内，不能再次相加。
- 时间：首次可信事件时间、时间来源；能观测到的改写时间另记，不能覆盖旧时间。只有时间范围就保留范围，界面可用约几点展示，但不能用显示中点制造精确归属。
- 模型：原始模型名、规范化版本；任务 ID、已知的父子关系、turn/request ID（存在才记）。任务标题、模式/推理档位等按任务或变化段保存，避免每笔重复。没有证据不能假设账号、主子关系或模式。
- 事件证明：来源身份、内容代际、累计计数重置段、旧/新指纹、事件关联和对账结果。指纹不能只按 Token 相等合并；不同任务及重置后的相同数值可能是不同调用。
- 周期：已确认周期及其边界证据、重置类型、账号/来源作用域和必要的额度观测。现有额度观测压缩/清理策略需要补充“已结束周期冻结”契约，避免历史周期随观测清理而消失。身份字段保留在内部，不恢复用户已要求去掉的繁杂标签。
- 计价：保存用量组件与采用的价格规则版本，使显示费用可解释、可复算；不把美元金额当作唯一事实。不借此修改现有 Fast 倍率或价格策略。

### 不进入长期账本

完整提示词、回答、推理全文、工具请求/返回、代码 diff、图片和上下文摘要正文。默认只存正式任务标题，不为所有调用预存提示词/回答摘录。需要正文时校验文件代际，再按需读取；原文消失后显示“原文已不可用”，数值详情仍可看。

若用户选择保留少量摘录，另设可关闭、可清除、有限字节预算的缓存，不影响账本完整性，也不能承诺原文在摘录创建前丢失仍可恢复。

### 可以重建或清理

图表桶、排行、汇总、扫描字节检查点、旧文件 chunks、暂存解析产物、可选正文摘录。账本只保留仍用于跨代对账的必要指纹和关联，不永久叠加每轮全库副本。

## 4. 旧账与新文件如何接续

1. **先保护旧账。** 启动后台解析/自动修复前，以 SQLite 一致性备份处理旧 DB/WAL；导入最近已发布逻辑态，保留未发布暂存但不计入总量。未知 schema 只读拒绝，不能清缓存重来。
2. **直接导入旧索引。** 保留数值、原始字段、质量分类和指纹；不以当前原文是否还能重放作为导入资格。已有可证明的旧会计错误采用有记录的修正，不能把所有旧数无条件视为正确。
3. **为来源建立内容代际。** 文件路径、offset、ordinal 均不能独立作为永久身份；路径移动/归档可关联回原任务。thread ID 也不等于所有记录归属，父任务继承片段必须单独识别。账号身份未知不跨账号合并。
4. **没有变化的文件不解析；正常追加仍走原检查点。** 源文件重写/截短、旧解析遗漏修复等只对受影响来源建立对账任务，不能全库重置 parser revision 强迫重扫。
5. **新旧重叠逐事件匹配。** 优先可信 request/turn/event 身份；没有时结合来源关系、完整累计/当次组件、重置段、事件顺序和邻近唯一锚点进行一对一匹配。保留重复出现次数，不能用简单集合去掉两个同数值的真实请求。被重写的时间、offset、ordinal不能作为唯一匹配键。
6. **匹配成功只入账一次。** 保存新原文定位，沿用可信旧时间与模型证据；字段冲突保留两侧证据并采用明确的优先规则。旧账没有的新调用经证明属于当前任务且未重复后补入，覆盖过去被遗漏的子 Agent 调用。
7. **原文中找不到的旧事件继续保留。** “缺少原文”不等于“消费不存在”。若证据确认原记录是继承重复/错误，则以可追溯修正排除，不能靠保持总数不下降掩盖错误。
8. **歧义不强行相加。** 对无法判断是否重叠的新候选保留证据，维持已发布旧账，不重复加候选；旧账本身已标记异常的保持异常。只影响对应范围和精确度，不使整库陷入重试。无歧义的新来源继续更新；受影响来源只有建立可信的新调用边界后才发布其后续增量，不能按迁移墙钟时间直接划线。
9. **事务发布。** 账本新增/关联/修正、来源检查点和受影响聚合同事务提交。断电只留下可恢复暂存，不能出现事件已记账但检查点未推进导致重复消费。

旧索引若只有汇总或累计种子：原样保全其证据，不反推逐次请求，也不新增“压缩前累计”费用类别。本机已被替换掉的旧明细必须找到真实备份才能按同精度恢复；方案保护未来，不能补造过去。

## 5. 功能降级要精确到缺失字段

| 已有信息 | 可保留功能 | 限制 |
| --- | --- | --- |
| 时间、组件、模型、任务齐全，正文缺失 | 总量、模型费用、日期/小时图、周期明细、任务/调用排行 | 原文不能查看；原文不存在不阻断统计 |
| 数值可靠、模型未知 | 总 Token、时间与任务统计 | 这部分不猜模型费用；已有可靠模型的费用可正常显示 |
| 数值可靠、时间不明 | 累计统计与能确定的任务统计 | 不塞进当前或任意历史周期；周期页说明有无法归属部分 |
| 父子关系未知 | 独立任务用量 | 不编造主子关系；历史保全任务不计为“正在运行” |
| 新旧重叠或组件异常尚未厘清 | 保留旧已发布结果和两侧证据 | 不重复累加；状态只针对受影响数据，不全局报错重试 |

累计/日图/模型/周期/排行必须从统一入账视图查询。周期边界有不确定区间时保留现有可解释规则，不把所有缺失都归为“那一分钟”。实时速率和 Agent 活跃状态仍来自近期实时数据，不因历史账本保留而虚增。

## 6. Release 与中间开发版本兼容

- 验证 v0.9.1 实际 Swift/Rust 旧结构，以及本轮支持的 Swift 6/7→11→12、Rust 9/10→11→12 路径；不能只测当前 12→新版本。
- 旧 legacy 文件、已 paginated 文件、两种混合，以及旧索引+已被上游裁短文件都须覆盖。结构迁移使用 SQLite 行，不触发原文全扫。
- 将“结构升级”“会计修正”“原文代际变更”分开标记与执行；一次组合候选转换，不因多个版本标记重复搬整库。
- 受影响文件可能必须完整读一次才能证明重叠；承诺按需定向、后台限速及可恢复，不承诺所有转换都能零读取。启动先显示已发布账本；大文件只开有限并发，扫描读取量有明确进度，不循环重试同一坏文件。
- 迁移成功不能只用 warm refresh 成功作为销毁旧库条件：须先验证旧已发布事件都已导入或有明确修正映射，再允许清理冗余迁移副本。账本唯一副本不属于清理对象。
- 旧版不能写新 schema；保留明确版本的升级前恢复副本。降级只能得到该时点旧快照，不能声称旧版能继续使用新格式产生的全部数据。不同应用版本与两端不能同时写同一活动库。
- 文件消失只标记不可用；明确“清除统计历史”必须同时覆盖持久账本、摘录与受管恢复副本，避免下次升级重新导入已删除数据。普通清缓存不得删除账本。

## 7. 空间与性能

现有精确索引约数百 MB，原 JSONL 约 30 GB；这是当前现场数量级，不是新方案的容量保证。建议通过整数外键、每任务一次元数据、紧凑指纹和有限 SQL 索引控制体积。每次调用保留数值事件，不默认降成日汇总，否则未来任意周期和排行无法重算。

迁移期间允许旧库+候选暂时双份；先查实际可用空间，不足则继续读旧账，不能删旧账换空间。成功后只留下新账本、规定数量的恢复材料，不按每次刷新创建备份。需要在真实旧库副本上量测总大小、每百万事件字节、迁移峰值空间、后台 CPU、增量读取量与查询时间后才能给出最终预算。

## 8. 实施次序与验收

1. 在隔离副本上建立账本 schema、数据目录迁移、保全先于替换/删除的门禁；证明结构升级原文 parser 调用为零。
2. 双端格式适配、旧事件导入及源代际对账；共用 golden fixtures，统一事件身份与入账结果。
3. 汇总/模型/日图/周期/排行/详情引用接入；补上已结束周期持久保存；缓存清理、文件删除、归档和用户清除流程分别验收。
4. 故障注入与性能验收后再替换本机应用。Windows 另做真实安装、文件锁、rename/fsync 与恢复测试，不以 macOS 构建代替。

最低测试矩阵：
- v0.9.1/中间 schema 已发布与 building 状态；future schema 拒绝；DB/WAL 一致性、磁盘不足及每个提交边界中断。
- 普通/子 Agent、fork 继承、裁短与未裁短、重写全部时间戳、EOF 前缀标记、累计重置、相同数值的不同调用、缺模型/时间/组件。
- 原文被删/损坏 UTF-8/仅部分可读、路径移动/同任务多副本、账号或 Codex Home 切换；正常新文件不被旧问题阻塞。
- 原文无匹配时旧账不降；重叠不得双计；确定旧错误可追溯修正；重启对账幂等；详情不能读错代际。
- 累计与各切片的可归属部分守恒，未知项不冒充精确；主子任务去重一致；实时状态不包括历史保留条目。
- 冷/热启动和 append 验证原文读取范围；迁移只处理受影响来源；无变化时不重复跑全库摘要、指纹匹配、VACUUM 或聚合重建。

## 9. 需要用户选择的产品取舍

技术上的去重、崩溃恢复、旧结构兼容和错误修正由实现负责，不让用户挑算法。

1. **历史保存期限**：建议数值明细长期保留，不自动过期；清理只清可重建缓存。若选择期限，必须接受期限前的任意区间/周期细节不可恢复。
2. **是否缓存少量正文摘录**：建议默认不保存，仅存任务标题与统计字段；可选有限摘录会增加敏感文本副本和空间，只改善未来已缓存部分的详情可读性。
3. **在 Codex 删除任务后的统计**：建议继续保留已发生消费，只取消原文入口；由 Bar 的独立“清除统计历史”动作删除对应账目。若要求随任务删除，应明确这会使历史累计下降。

其余建议默认：歧义保留证据但不重复加账；不确定范围给简短局部说明；不新增复杂常驻标签；程序不自动为追平旧总数添加没有组成明细的费用。用户明确填写的手动补差按下一节独立保存。本轮仅完成方案，这些推荐默认不构成继续追问或阻塞方案完成的事项。

## 10. 后续功能：手动补差

### 用户操作与展示

- 在累计统计的管理入口增加“手动补差”。用户可单独填写 Token 差值、金额差值（USD），或两者都填；允许正负调整，支持明确的 Token/万/亿单位，提交前显示原累计、此次调整和调整后累计。
- 第一版仅调整累计口径，不强行指定日期、模型、任务或额度周期；可选备注解释原因。不是伪造一条调用，也不是写入供应商账单。若以后需要周期级调整，另做明确范围设计。
- 一次提交记录固定差值；不能持续反算成某个目标总数，从而吞掉后续真实新增。如果以后加“目标累计”输入，也只在保存时按明确的同一账本快照换算一次差值。
- 只有存在非零有效补差时，累计附近提供简短“含手动补差”入口；点开可看自动统计、手动调整及最终合计。其余主界面不增加冗长标签。
- 调整可查看、修改和撤销；撤销后恢复其数学影响，不需要重新扫描。负调整后总数不得为负，输入必须有限、合法、在安全整数/固定小数范围内，不能静默截断。

### 数据契约

- 独立 `manual_adjustments` 逻辑表，与来源 events 分离，放在持久账本数据库中。保存 UUID、作用范围（当前统计数据集）、有符号 Token 整数、有符号 USD 固定精度金额、创建/修改时间、备注、修订/撤销状态以及填写时账本快照标识。
- 原数值事件保持不变，修订保留简短审计轨迹；数据库事务与幂等 ID 防止连续点击、重启重试或备份导入产生多次调整。两端遵循相同字段/计算规则，各自存储，不因共享 Codex Home 自动叠加对方的调整。
- 采用有界整数和固定精度金额；不通过 JS 浮点格式化后的文本参与账本计算，不将输入 Token 按某个模型价格自动换算金额。
- 账本总览：`显示累计 = 自动统计累计 + 有效手动差值`。分模型、按日/小时、周期、请求次数、排行和真实事件导出仍基于自动账本；手动差值没有这些维度，不能冒充它们。总览可展开解释“各明细汇总 + 手动补差 = 显示累计”。
- 实时 Token 速率、运行 Agent 数、5h/7d 官方额度百分比、雷达站、额度反推/本地区间测算，均不使用全局手动差值。金额调整只改变累计展示，不改价格规则或历史请求计价。
- 全量重建、缓存清理、价格/解析器升级、来源删除不得清除手动记录；显式“清除统计历史”应说明并覆盖对应补差和受管恢复材料，避免旧备份再次导入后复活。
- 后续如果主动导入旧备份恢复历史，先显示实际可入账新增量以及已有补差。不能自动假定二者对应并抵消，也不能无提示地同时加两遍；由用户在具体恢复预览中决定是否修改原补差。补差值不能用于对账证明或触发重复扫描。

### 实施与验收边界

手动补差在持久账本及保全流程完成后实现，Swift/Tauri 同步提供；已经纳入授权实施范围，但当前尚未实现，不代用户填写差额，也不提前宣称上线。

需验证：Token 单独/金额单独/同时调整、负数与撤销、单位换算和上限、重复提交、并发新增用量、进程中断、重建后保留、备份导入去重、数据集切换隔离、双端一致、实时/周期/模型统计不受污染，以及主动旧账恢复与既有补差的冲突预览。
