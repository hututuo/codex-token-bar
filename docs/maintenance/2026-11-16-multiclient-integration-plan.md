## 1. 交付目标与结构

用户在主页、24小时曲线和方块热力图中，都能选择单客户端或汇总；相同功能使用同一套展示组件、字段含义和状态规则。支持额度的客户端，其当前额度、历史曲线和额度热力图贯通；缺少额度来源的客户端明确显示能力状态。

沿用以下路径：

```text
各客户端本地读取器
  → 现有用量账本 / 额度历史
  → 规范化用量与额度结构
  → 单客户端或汇总投影
  → 原统计卡、折线图、热力图、额度条、缓存排行

Codex 原精确账本与账户额度服务
  → 原有适配器
  → 同一展示投影边界
```

这里的“统一接口”是跨端一致的数据契约和每端复用组件。Swift、Rust、TypeScript保留各自实现，通过共享样例验证语义一致。读取器处理各软件格式差异，页面只消费规范化结果。

这次优先补热力图缺口。已接好的24小时/7天/30天曲线、统计卡、缓存排行作为回归基线，避免重复建设。build 1021的Antigravity四等宽额度和二级侧栏完整标签、小数布局继续复用。

## 2. 入口与用户交互

| 区域 | 客户端范围 | 额度来源与周期 | 默认行为 |
| --- | --- | --- | --- |
| 主页 | Codex / 各客户端 / 汇总 | 每个客户端展示自己的窗口 | 沿用当前选择及“更多”菜单 |
| 24小时/7天/30天曲线 | 跟随主页 / 各客户端 / 汇总 | Codex、Claude CLI、Claude Desktop、Antigravity · Gemini、Antigravity · 第三方模型 | 保留当前图表选择逻辑 |
| 方块热力图 | 补齐与折线图同语义的“跟随主页 / 各客户端 / 汇总” | 仅额度模式显示来源和5h/7d选择 | 默认跟随主页，额度周期默认7d |
| 侧栏 | 沿用侧栏独立范围和隐藏设置 | 使用同一额度提供者与展示规则 | 不受热力图临时选择影响 |

热力图复用现有范围选择逻辑与样式，使用独立的偏好键，不覆盖折线图的选择。切换范围后重新计算格子、悬停明细、日期选区总计和图例；失效的悬停对象及时清除，合法日期选区保留。

“汇总”下Token、调用、已知金额可以相加；缓存命中率使用输入Token加权。额度仍通过来源选择查看，标题始终带客户端与额度池，不计算多个账户或额度池的平均“总额度”。

统一保留七种热力图模式入口：每日、每周、累计、模型占比、模型费用、缓存命中率、额度。用能力和当前数据状态替换 `tokensOnly` 的整体屏蔽。模式支持但某日缺数据时，该日显示“未记录/字段不完整”；客户端没有额度能力时，额度模式显示“尚无本地额度来源”，不画0%格子。

## 3. 第一阶段：补齐日数据契约

这是后续接线的前置工作，先解决数据是否足够，再开放模式。

### 3.1 用量日桶

继续使用现有 `dailyBuckets` 路径，按“客户端 + 本地日期 + 原始模型”分组。已有 `ClientTrendBucket` 的模型、金额、缓存完整性字段优先复用；只为无法表达的日级覆盖状态增加可选字段。

| 数据 | 接入要求 |
| --- | --- |
| 客户端与模型 | 保留client和原始model；展示名称和颜色使用现有模型映射，同名模型跨客户端不混淆 |
| Token与调用 | input/output/calls可加；cache read、cache write是输入的组成部分，不能重复计入Token |
| 缓存完整性 | 按日、按模型判断，不用整个客户端累计记录的完整性替代某一天 |
| 模型覆盖 | 区分完整、部分、未提供；缺少模型标识的用量保留在未知模型中 |
| 费用 | 复用现有逐请求计价入口后累加，保留微美元精度及 `unpricedRequests` |
| 数据版本 | 投影绑定账本修订与来源范围；异步结果只发布到匹配的当前选择 |

费用必须保留请求时点、阶梯价、缓存写入时长等现有规则。热力图直接接收已计价小计及完整性，不能把日Token合并后交给Codex模型别名重新估价。界面继续使用“API等值/已知金额”语义，不将其称为用户实际订阅账单。

旧快照缺新增字段时，Token仍可用，对应模型或金额标为待读取。空日、确知零费用日、全部未定价日要可区分；部分日期或模型未知不能抹掉其他已知金额。

## 4. 第二阶段：贯通热力图所有用量模式

数据契约完成后，沿原组件接入：

1. 缓存模式使用日桶的完整性和原始输入/命中量；日期范围结果按总命中量除以总输入量计算，不平均百分比。
2. 模型占比从完整日模型投影读取。Swift当前 `modelShareSummaries` 依赖Codex的 `attributionEvents`，因此仅补 `dailyModelBreakdowns` 不够，要让模型占比、费用、悬停和选区共同消费日投影。
3. 费用模式接收已计价金额。Swift的 `modelCostSummaries` 和React的 `modelCostUSD`、`rangeSummary` 都要避免对外部日合计重新计价。
4. 去掉混合日期“整天丢弃Codex模型明细”的退让处理；改为保留Codex已知部分、接入外部已知部分，并单独说明缺口。
5. 365个本地日历日期完整保留。无用量、未知、未接入采用现有色系下不同的状态文字和可访问标签，不靠同一种空白解释所有情况。
6. 按第二节接入独立范围选择，清除切换后遗留的客户端名称、图例和旧选区内容。

修改位置：Swift的 `DashboardView.swift`、`TokenActivitySection.swift`、`TokenHeatmap.swift`、`TokenHeatmapData.swift`；React的 `DashboardAnalyticsSection.tsx`、`TokenActivitySection.tsx` 和 `components/tokenActivity/` 内的数据、悬停、范围汇总、模式选择模块。

完成条件：七个客户端及汇总都能查看可用的Token、缓存、模型和费用；格子颜色、悬停明细、选区总计来自同一投影，数据不完整只影响对应指标。

## 5. 第三阶段：贯通额度热力图

### 5.1 复用现有额度链路

当前额度条、额度曲线和热力图使用同一来源目录与池映射。沿用 `ClientQuotaReading`、`ClientQuotaHistory`、`ClientQuotaChartSource`，读取现有 `client_quota_observations`；Codex仍通过原 `QuotaHistoryStore` 适配。

Antigravity的映射固定为：

| 来源 | 5小时 | 7天 |
| --- | --- | --- |
| Gemini池 | `gemini-5h` | `gemini-weekly` |
| 第三方模型池 | `3p-5h` | `3p-weekly` |

不把模型列表当额度池。Claude CLI和Desktop分别保留来源；缓存、官方本地历史与RPC读数的来源身份不互相覆盖。已有账号身份可以使用时要继续保留；未知账号不能标成“当前账号已验证”，检测到切换时应分段，不能拼成连续的同账号历史。

### 5.2 日格子的定义

当前Codex日额度桶采用有效观测的算术平均，热力图颜色使用7d。第一版沿用这一日级统计口径，补齐客户端、来源、池、周期和样本说明：

- 一个格子表示“该日该额度池、该周期的有效采样剩余额度均值”，不表示全天实际可用比例或当天消耗量。
- 增加5h/7d切换，默认7d；悬停展示两周期均值、各自样本数、首末观测时间与来源。
- 日均值只计算真实有效观测，不将曲线为连续显示而短暂延续的值当成额外采样。
- 日期范围显示“有观测日的日均剩余额度均值”，同时显示覆盖天数；不将缺失日按0%计入。
- 重复读取同一缓存保留原采样时间，不增加新样本。官方重置之后没有新数据时，历史只到实际观测，不自动补100%。
- 原始额度保留小数精度；显示沿用现有最多两位、去除尾零的统一格式。

补充日聚合读取接口，按需读取最近365个本地日期的已有记录；折线图仍保持原30天明细窗口与读取上限。数据库中只有30天记录时，其余日期明确空缺。不会从远端补历史或由Token倒推额度。

Swift的 `ClientQuotaHistory.swift` / `QuotaHistoryStore.swift` 和Rust的 `client_quota_history.rs` / `quota_history/series.rs` 负责日聚合；React的 `clientQuotaHistory.ts` 负责适配。复用图表的来源选项构造逻辑，热力图选择独立保存。

完成条件：Codex、Claude CLI、Claude Desktop、Antigravity两池都能进入同一额度热力图；与原始观测手工算出的日均值一致，重置、缺口和重复缓存不产生虚假额度。

## 7. 数据库、兼容与性能

第一至第三阶段以查询和展示投影为主，目标是不迁移原用量账本、不重写历史事实、不另建业务数据库。现有表能派生的数据先从现有表读取。确需索引或持久化派生缓存时，先提供查询测量及旧版本兼容验证，再做可重建的增量结构。

性能约束：

- 365天费用不放到主线程计算，不在鼠标悬停、范围切换或每次额度刷新时重新扫全年明细。
- 日投影缓存包含账本修订、日期边界、时区、价格资源版本和数据源配置。范围选择过滤已有结果；不增加数据源扫描。
- 用量更新影响哪一天、哪个模型，就优先失效对应派生数据；重复修订和无变化刷新复用结果。跨日、时区变化及价格规则变化有明确失效入口。
- 后台任务沿用generation/cancellation机制，旧范围的迟到结果不得覆盖新范围。
- 无变化刷新、首次日投影和增量更新分别记录耗时、行数和峰值内存，与build 1021同一脱敏样例对比。出现每分钟全年重计价或随悬停查库即不通过验收。

升级验证使用小型、可复现的旧库夹具与只读历史摘要；保留原有账本、修订、来源身份和回退App，不为一次UI接线复制大量真实数据库。

## 9. 完成的判断

“已完成统一接入”同时满足：相同数据契约、相同组件、单独与汇总入口、已知/未知正确表达、历史可保留、刷新可复用、macOS/Windows路径齐全，并有相应层级的测试和实机证据。只有读取器、按钮、截图或云端包中的任一项，都不能单独作为完成证明。

重置卡、Codex共享额度反推、Codex雷达继续按其服务能力显示。众测雷达服务故障另列问题；实时速度保留各来源的测量含义，不能为统一样式把外部活动速度标成Codex正文TPS。
