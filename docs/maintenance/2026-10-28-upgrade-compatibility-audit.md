核查基线：`codex/startup-and-local-quota` / `3a945511`。范围为用户从旧版升级至当前源码，包含 Mac 原生和 Windows/Tauri。未打包、安装、重启正式应用、修改真实账本或网络规则。本报告未修复下面的问题；产品代码保持原样。

## 结论

普通升级的已有回归通过，但暂不建议据此发布：发现两类迁移失败后的恢复缺口。第一类双端存在，Mac 已用临时目录中的真实 SQLite 夹具复现；第二类是 Windows/Tauri 的代码路径缺口，尚未做进程断电注入。旧文件保留，不等于升级后的显示已完整。

## 1. 未完成导入被当作已完成，重试可能少算（发布前须修）

### Mac：隔离测试已复现

1. 建立并激活 A 库，关闭测试路由。
2. 新增一个待导入旧模块库，含一条记录。
3. 导入后在最终激活前注入失败。
4. 在保留的旧模块库新增第二条记录，模拟失败后旧程序继续使用或旧文件恢复。
5. 重试迁移：没有报错，但 A 中只有一条，期望两条。原文件仍有两条。

`BusinessDatabaseMigration.swift:118-119` 仅凭 `tb_legacy_inputs` 判定来源已完成；该表在 `:212` 写入，发生在最终复核 `:225-232` 和激活 `:236` 之前。已有 A 的未完成补导入，重试时不会回到复核队列。

证据：`scratch/upgrade-compat-repro.log`；测试方法保存在 `scratch/upgrade-compat-repro-test.txt`。临时方法验证后已从测试源码移除，没有留一项失败测试混进正常测试集。

注意：成功激活后的旧文件是冻结的回退证据，不能在普通启动时重新覆盖 A。应修复的是“本批尚未完成的导入”，而不是每次启动都重新导入旧库。

### Windows/Tauri：同类代码路径确认

`business_store_container.rs:701-708` 在导入事务里提交来源收据；`business_store_route.rs:482-490` 随后才复核原文件。复核失败时初始化 marker 尚未发布。重试经 `:368-385` 看到收据就跳过，`:417-420` 返回既有分区，因此下一次 bootstrap 可能完成，却遗漏变化后的来源记录。

已有测试只验证成功初始化后的旧文件变动被忽略，这是正常行为；未覆盖未完成批次的重试。

### 修复方向

双端统一区分导入中、已核对、已激活。未激活批次重试必须重新核对来源；若来源发生变化，只重建该未激活导入结果，不覆盖已激活分区的新账。激活结果和完成状态必须有明确、可恢复的提交边界。补失败前后、来源变化、不变、已有 A 新账保留等回归。

## 2. Windows/Tauri 不完整备份可能导致重试一直失败（发布前须修）

`business_store_route.rs:394-400` 使用确定性备份路径，已有文件就不重新创建；`business_store_container.rs:308-330` 直接在该目标写在线备份。进程在生成过程中中断，留下空库、部分库或校验不符的文件，下次依然复用该文件，校验反复失败。原文件不会被删除，但用户可能一直停在升级失败页。

证据级别：代码审查确认恢复分支缺失，未运行真实 Windows 中断测试。Mac 使用每次尝试独立 UUID 的备份路径，没有这一个确定性路径复用问题。

修复方向：备份写唯一临时路径，完整性及内容核对、落盘后再原子发布；已存在但不完整的候选隔离保留，再生成新快照，不能把“文件存在”当作“备份完成”。

### Mac 主 schema 范围

从本地 Git 发布标签核对：v0.9.1 为 schema 6；v0.9.2/v0.9.3 为 13；v0.9.4 至 v0.9.7 为 14。当前接受集合是 6、7、11、12、13、14，覆盖上述发布标签的主版本号；具体结构及其他账本版本仍需校验，不是仅改数字就放行。已有 schema11 迁移测试覆盖账值、计数及失败回滚。

更老的 2/3/4/5、未知未来 schema：原样保存在隔离分区，闲置 Home 不阻止正常 Home 启动；如果它恰好是用户当前使用的 Home，则仍拒绝读写并报版本不支持。因此不能宣称支持任意老版本跨级直升。这一限制也存在于 v0.9.2 后的支持集合中，并非本次才移除旧转换。
