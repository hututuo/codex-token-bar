# 暂存池索引整段回填复测

用户要求重新测量此前“加索引后更慢”的结果。本轮不改产品源码、不重建二进制，使用同一份旧版和候选版执行完整生产fixture。所有数据在新建的隔离合成目录中；没有打开正式数据库、停止用户应用或调整并发写入探针的250毫秒时限。

## 固定对象与口径

- 旧版源码`6101769e`，二进制SHA256：`9ce053d11d6ded6c38c6567bf462f5f9b666d35e2789a055df1368c37cf1d42d`。
- 候选源码`b18fc185`，二进制SHA256：`0edc43c1eeef49b21bdc4d42cf88570135e4137a962c009853550f5368511702`。
- 每次4124来源、503128事件、2515640 tokens、6250保留旧空候选。成功运行逐文件比对4124个原始输入，与之前记录字节相同。
- 回填时间只含历史字段补全、随后一次普通sync和summary。初始账本/历史候选准备、20次普通刷新采样及最终恢复核验均不含在回填时间中。
- 每30秒及阶段变化时记录系统load average、前12个高CPU进程、测试进程累计CPU时间及可用空间。阶段边界来自2秒轮询；CPU差值另含回填后紧接着的账目核验，不能把它当作精确的回填CPU计时。

仍是顺序运行，数据库由各轮重新生成，不是还原同一个冻结数据库镜像；原始输入相同不代表物理页布局和缓存相同。运行期间后台负载未控制，记录的相关性不是因果证明。

旧版首次在回填途中因并发写入探针报`SQLite Some(DatabaseBusy): database is locked`而退出，producer exit=1；不是600秒性能预算失败，也不是输入/源码发生变化。810.670秒是从整个测试进程启动到失败的总时长，包含数据准备，不能当成回填时间。失败时没有完整scale报告，不能与成功运行作耗时比较。

候选版16项生产场景全部通过，事件ID/值/类型账目摘要前后均为`442df884874a33dc15d2c5a07ef61c7aae3a52d35de9863d7459e290e4716e3d`，warnings=0，旧空候选、回执和原始数据保留。候选二进制此前两次回填为473.792及481.890秒，本次相同二进制363.670秒；这证明单次时间有显著波动，但不能单独证明波动来源，或证明索引有净收益。

旧版重试同样通过16项生产场景及全部规模账目检查。有效对照中候选回填少49.348秒（11.95%），普通刷新P95多0.178秒。两者回填时load average均值分别约10.86和10.75，范围分别为7.67–18.05、6.78–18.20；平均值接近不代表CPU调度、磁盘或缓存条件相同。阶段观察所得“回填加紧随其后的账目核验”进程CPU时间为候选305.43秒、旧版311.85秒，差约6.42秒；不能把49.35秒墙钟差值全部归因于CPU工作量减少。

本轮没有复现候选回填持续更慢，但尚未建立隔离负载、固定数据库镜像的因果对照。该索引继续保留为本地候选，不以一次12%改善承诺稳定加速。整个测试进程时长分别1510.390秒与1398.657秒，含准备、20次刷新及多项恢复核验，不能代替回填耗时。

## 证据

`scratch/pool-index-retest-20261106/`：三轮各自的`.log/.producer.json/.validation.json`，以及最终`comparison.json`。该目录保留失败的旧版首轮，不覆盖为重试成功。`.validation.json`记录二进制hash、全部Rust源文件hash、负载采样及执行前后稳定性。

另做了宿主SQLite 3.54.0的内存查询计划检查：按job_id查找仍走主键，发布receipt/消费generation两条SQL会改走新索引；这只是辅助线索，既非产品bundled SQLite 3.50.2的计时，也未证明是性能回退原因。

## 后续反向顺序复测

用户再次要求重测后，固定相同二进制按旧版→候选版执行：旧版回填330.104秒、候选349.260秒，候选慢19.156秒（5.80%）。两版全部规模与账目检查通过，方向与本报告上一组相反，因此仍不接受稳定净提速。另用同库bundled SQLite热缓存交替微测确认：任务查询由约2.0～2.9毫秒降到0.014～0.016毫秒，快约130～200倍；这不等于整段回填同幅度改善。详见[反向顺序复测](2026-11-06-pool-index-reverse-order-retest.md)。
