# 暂存池候选索引：写入代价与查询收益

结论：建议保留 `b18fc185` 中的候选索引，作为减少重复扫描的局部改进。查询收益已经实测；索引也确实增加写入工作和空间。本次隔离实验没有复现稳定的十几秒写入惩罚，但不据此承诺完整回填固定加速。之前将“整段尚未稳定提速”直接作为不接受索引的理由不充分，应按实际读写权衡决定。

产品源码未修改；当前仍是本地候选，未合并、安装或发布。实验只读取已完成的合成夹具并写入新建的隔离库，没有访问正式用户数据库。

## 它具体影响什么

这是现有 A 数据库、现有暂存池 `jobs` 表内的一条局部索引，不是另一个数据库。只收录 `state='sealed'` 的任务头；不是给每条 Token 或事件增加索引。

| 操作 | 对索引的影响 |
| --- | --- |
| 注册 building 任务 | 检查局部索引条件，不加入条目 |
| building→sealed | 插入一条索引记录 |
| 关联 pending_generation | 不是索引字段，不增删条目 |
| 写发布回执、sealed→consumed | 查询计划可以使用索引；消费时移除索引记录 |
| consumed→reclaimed、删除载荷 | 任务已在索引外；仍有少量条件判断 |
| 重建、回填、恢复时寻找可复用暂存任务 | 从按来源定位代替反复扫描历史任务头中受益 |

直接调用位置是 `stage_or_reuse_full_rebuild`→`staging_database_paths`→`Pool::candidates`。普通无变化刷新、面板总额和图表查询不是这条候选查询，不能声称它们也快了百倍。候选查询在共享 Pool 锁内执行，减少扫描有利于缩短该部分持锁工作，但本次没有测量并发锁等待收益。

## 对照方法

在 `1545c916` 对应源码上，使用产品 SQLite 3.50.2 dylib。读取保留的候选夹具 `tokenbar-pool-index-scale-lrhhpadt`，冻结 8272 条任务头中的一轮 4124 个来源。起点包含另外 4148 条历史任务头及相应 operation/receipt，其中一条仍为 sealed。两边每次从同一页镜像复制起点，唯一结构差异是是否创建候选索引。

原样使用六张 pool 表、14 个触发器，并从当前 Rust 文件提取注册、封存、pending、回执、消费、回收 SQL。写入测试不执行候选 SELECT，防止把已知查询收益混入写入代价。发布 SQL 自身因索引而改变的执行计划则保留，因为这是添加索引的真实影响。

先运行五组交替顺序的内存对照，再运行三组交替顺序的磁盘对照，未并行运行两类负载。磁盘库采用 WAL、synchronous=FULL、foreign_keys=ON、2MB cache、wal_autocheckpoint=1000；注册、封存、pending、回收各为每来源一个事务，回执与消费共用一个事务，提交单独计时。建索引单独计时，不并入后续写入合计。

每阶段结束都在计时外核对全部六表的带类型行摘要。8 组对照、16 次执行均通过，相同阶段摘要在内存/磁盘及有/无索引之间一致；最终摘要为 `5f35514388184565bd6052919af43c61006e1ed19e518c0b7c42a79d7e659d1a`。外键及 quick_check 通过，三个负控确认不完整封存、修改封存事实、无回执消费均被原触发器拒绝，产品源文件 hash 前后稳定。16 个来源的 smoke 仅验证脚本，未纳入性能数据。

## 一次建索引

本起点 4148 条历史头、一条 sealed：内存五次中位数 0.002068 秒；WAL/FULL 三次为 0.005206、0.005389、0.029401 秒，中位数约 5.4 毫秒。这里测的是 CREATE INDEX 与提交，不包含产品完整迁移的身份/合同核对和登记步骤，也不代表大量 sealed 积压时的建索引时间。

原完整规模测试在回填计时前已建好索引。因此先前 330.104→349.260 秒的 19.156 秒差值不是首次建索引耗时。

## 4124 个任务的写入侧

下表是每一对“有索引−无索引”的差值中位数，正数表示增加，负数表示本次较快。每个阶段都处理全部 4124 个任务；不是单任务耗时，也不是完整应用回填耗时。各行中位数不能相加当作整段中位数。

| --- | ---: | ---: | ---: | ---: |
| 注册 | -0.0584 | -0.0224 | +0.0114 | 0 |
| 封存 | +0.0134 | +0.0787 | +0.0873 | +10945 |
| pending 关联 | +0.0049 | -0.1131 | -0.0167 | 0 |
| 发布回执 | +0.0219 | +0.0431 | +0.0436 | +207 |
| 标记 consumed | +0.0372 | -0.0018 | +0.0353 | +2665 |
| 提交发布事务 | -0.0006 | +0.0387 | +0.0350 | 0 |

封存加发布（回执、消费、提交）的线程 CPU 配对差值分别为 +0.1430、+0.2314、+0.1501 秒，中位数约 +0.15 秒。这是上述四个具体阶段的计算时间代价，不是整个回填额外等候时间。单独把发布三阶段相加后，墙钟配对差值为 +0.0802、+0.0821、-0.1004 秒，同样存在波动。

确定的工作量代价比墙钟更稳定：三组 WAL 对照均多 123580 个 SQLite VM 指令、多 13817 次 cacheWrites。以每页 4096 字节折算，后者约为累计 54 MiB 页面载荷写出，可能反复写同一页；不是数据库永久增大 54 MiB，也不是包含 checkpoint、文件系统放大后的实际物理磁盘写入量。注册、pending、回收均未增加该计数。

发布回执不是“没有新增 VM 指令就一定更快”的例子：原计划扫描 jobs，新计划按 owner 走候选索引；总 VM 减少 24815，但 CPU 与页面写出增加。本组 sealed 数较多，索引遍历顺序、回表和回执插入会影响局部性。已直接确认计划改变；没有把每一项底层代价进一步归因为唯一原因。

全部已测写入阶段之和（不含建索引、载荷批量插入和核验）：

| WAL 对照组 | 无索引（秒） | 有索引（秒） | 配对差值（秒） |
| --- | ---: | ---: | ---: |
| 0：无→有 | 4.5161 | 4.5270 | +0.0109 |
| 1：有→无 | 5.1707 | 4.6054 | -0.5653 |

WAL 合计配对差值中位数 -0.5653 秒；内存五组为 -0.1804、+0.1828、+0.0609、-0.2200、-2.2406 秒，中位数 -0.1804 秒。后台负载仍有变化，内存最后一组尤其明显，所有样本保留。因此不将负数解释为索引能让纯写入稳定变快，也不声称写入成本为零。可支持的结论是：在本次明确范围内没有测出稳定的十几秒写入总惩罚；维护确实多做工作，观察到的直接维护阶段计算代价为小数秒量级。

## 空间

4124 个新任务均封存时，索引占 691 页、2830336 字节，约 2.70 MiB；此时另有一条历史 sealed 任务。消费后索引仅剩一个 4096 字节叶页，但空闲页留在 SQLite 内供后续复用，不能说空间立即退还操作系统。

三组均得到同样的最终库大小：无索引 47091712 字节，有索引 50065408 字节，文件差约 2.84 MiB。任务完成后不再占用索引条目；索引规模主要随同时 sealed 的任务增长，不随所有已完成历史头线性增长。没有运行 VACUUM 或清理历史数据。

## 查询收益与取舍

沿用上一轮同库热缓存 SELECT 测量，不重复跑全量回填：8272 条任务头，三类参数交替八组、每组 25 次，返回值一致。不存在/已消费来源从 2.62–2.88 毫秒降至 0.014–0.015 毫秒；有一条 sealed 结果从 2.00 毫秒降至 0.0156 毫秒，约 128–199 倍。包含 prepare/bind/step/decode/finalize，不含锁等待与写入。详见[同库查询记录](2026-11-06-pool-index-reverse-order-retest.md)。

这条查询发生在回填/重建/恢复内部，收益可以在同一轮任务中出现，不只发生在回填后的长期使用中。每次少扫描历史任务头是已确认的收益；不得把单次微测节省直接乘来源数，冒充整段已测净节省。

用户接受合理写入成本换取频繁查询更快。按这一标准，局部索引的维护和空间代价值得承担，建议在当前修复中保留。完整回填历史对照一组候选少 49.348 秒，另一组候选多 19.156 秒，均保留为真实但未控制因果的测量，既不证明固定整段加速，也不证明索引必然使整个回填变慢。本次不再以单轮完整耗时方向来反复撤销/恢复该实现。

## 边界与复现证据

这是提取产品 SQL 和原触发器的 SQLite 诊断实验，不是 Rust facade 或完整应用运行。它只含六张 pool 表，未复制其他命名空间与约 25000 个旧 catalog 对象；每个新任务的 event_rows/fingerprints/chunks 各放一条代表性载荷用于触发实际外键和回收校验，不含原始日志解析、真实批量载荷、restore、统计发布、Pool 锁竞争或并发写入探针。操作按阶段分组，不完全复现应用逐来源穿插的时序。阶段间摘要读取也会影响下一阶段缓存。WAL/FULL 提交覆盖此处 pool 写入，不代表完整账目发布事务的 fsync 或真实断电测试。不能据此给整个 330–349 秒回填的索引净影响设精确值或上界。
