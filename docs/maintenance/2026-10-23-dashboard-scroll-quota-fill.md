# 主界面滚动争用与一级额度条修复

日期：2026-10-23。基线 `268e854a`；工作分支 `codex/dashboard-scroll-quota-20261023`。

用户报告主界面滚动仍卡顿，一级贴边栏还在但额度色条消失。现场确认运行物是 `/Applications/Codex Token Bar.app` build950，PID96734；上一轮侧栏窗口动画修复尚未安装。主界面能够读到7天额度剩余4%。用户截图中轨道和白色参考线存在，中间额度填充消失，上下速率及模型占比仍有颜色。

## 额度条为何会消失

`QuotaSidebarRail.bar` 正确读取7天额度，也支持只有7天、没有5小时窗口的账户。问题发生在绘制末端：它向 `SmoothRateFillBar` 传入单一紫色，`SmoothRateFillLayerView` 原样赋给 `CAGradientLayer.colors`。该图层在只有一个颜色时不绘制渐变填充。

这不是“只剩4%所以看不见”的解释。新增原生像素测试在46×4pt轨道、2倍渲染下复现：4%与100%输入均为零个可见颜色像素。修复是把单色复制成相同的首尾两个颜色，得到实心色条；多色分段速率不变。相同测试随即通过。

没有把4%虚增为较大的比例，也没有把剩余额度改成已用额度。用户看到的白线仍是期望剩余量参考线。生产控制器的7d-only截图覆盖左/右边缘和4%/100%，4%时底部紫色短条可见，100%完整填充。

## 为什么另一个窗口会影响主界面滚动

主界面、悬浮窗和侧栏共享同一个 AppKit 主线程。滚动时，开启的悬浮窗仍接收实时速率更新。对真实build950进程采样，发现 `TokenDisplayCard.body` / `FloatingPanelPresentationModel` / `pagedContentDescriptors` 多次进入 `FloatingTodayModelUsagePresentation.items`，重新合并模型、解析历史价格区间并计算费用。速率变化时，今日模型的历史用量往往没有变化。

第一次采样含辅助功能树读取开销；第二次只进行滚动、在采样结束后读取整棵树，减少该干扰，但CUA滚动定位自身仍有辅助功能调用。这些采样用于定位调用路径，不作为硬件帧率、空闲CPU或精确耗时基线。现有图表准备工作在后台线程，不能因它出现在进程采样中就认定为主线程阻塞。

新增 `FloatingModelUsageCache`，由 `FloatingTodayModelUsagePresentation.items` 统一使用。费用行、占比、分页和无障碍文本现在可复用同一派生结果，最多保留四组输入，按最近使用顺序淘汰。缓存键包含完整模型用量、历史价格区间、回退价格模型、占位开关和Auto Review合并开关，不以数组数量、总token或时间戳近似判断相等。

缓存只驻留内存，不修改账本或价格计算公式。锁仅保护查找与存储，费用计算在锁外执行，避免后台调用正在计算时让UI等待。并发未命中允许重复计算相同结果；没有引入等待队列或无限历史缓存。`makeItems` 保留原纯计算，方便语义及复验对照。
