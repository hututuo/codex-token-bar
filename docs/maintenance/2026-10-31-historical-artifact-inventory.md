# Token Bar data and migration artifact inventory

This is a source-code inventory of app-owned data paths and generated migration remnants, not a cleanup authorization. It covers the repository's release tags `v0.8.0`, `v0.8.2`, `v0.8.3`, and `v0.9.0` through `v0.9.9` (there is no local `v0.8.1` tag). It does not inspect files inside a user's real support/cache folders.

## Roots and release transitions

`tauri-app/src-tauri/src/core/app_paths.rs` defines the Tauri roots. On macOS, the app support/cache bases are `~/Library/Application Support` and `~/Library/Caches`; on Windows they are `%APPDATA%` and `%LOCALAPPDATA%` (with documented fallbacks). Tauri data is under `CodexTokenBarTauri`; the older Swift app's support data is under `CodexTokenBar`. Swift Exact indexes use a separate `CodexTokenBarSwift` root. In this inventory, A is `codex-ledger.sqlite`; B is `multi-client-usage.sqlite` (native Swift places it in `CodexTokenBar`, Tauri in `CodexTokenBarTauri`, except isolated preview/demo paths).

The path history that explains otherwise surprising duplicates is:

- `v0.8.2` through `v0.9.1`: Swift Exact history was stored under `Caches/CodexTokenBarSwift/exact-usage-history-v1/<home-hash>.sqlite`.
- `v0.9.2`: `CodexUsageHistoryIndex.relocateLegacyIndex` began copying that database to the corresponding Application Support path. The copy includes committed WAL data and a migration-retention receipt; the cache source is intentionally left in place. A same-name cache/support pair is therefore expected and both copies may contain unique history if the support copy was subsequently written.
- `v0.9.8` and `v0.9.9`: the Swift and Tauri business-ledger import/migration code is present. It moves logical stores into `codex-ledger.sqlite` while retaining source files and verified snapshots.
- Tauri's active cache namespace is `tauri-usage-cache-2026-07-v6`; current code explicitly knows retired `v3`, `v4`, and `v5` namespaces. The active namespace constant is present in each inspected tag; retired namespace targets are enumerated in later tags. The Exact index below a cache root is durable history, even though its parent directory is named “Caches.”

## SQLite and cleanup rules

Treat every SQLite primary file and its `-wal`, `-shm`, and `-journal` members as one live/recovery family. A nonempty WAL can hold committed changes. The migration code uses SQLite backup APIs specifically to capture a consistent view; a raw main-file copy or sidecar deletion can lose history or break recovery.

The Tauri container compaction code checkpoints and runs `incremental_vacuum` only for containers created with `auto_vacuum=INCREMENTAL`, subject to free-space and fragmentation thresholds. Existing v1 containers are deliberately not fully vacuumed to change modes because rowids may be used by preserved legacy tables. This compaction creates no separate backup artifact; it does not authorize cleanup of source or snapshot files. Swift quota-history compaction is in-place as well.

The only patterns explicitly classified by current path code as discardable are the individual aggregate/snapshot JSON cache leaves in `discardable_usage_cache_cleanup_targets`. Even their production cleanup is deferred in the current ledger-migration release. All SQLite histories, migration snapshots, schema candidates/rollbacks, stages, quarantines, provider backups, and unknown files require proof-based ownership and receipt/manifest checks. A path name, mtime, file count, or marker alone is not enough to establish that another copy contains all history.

## Path/stat-only observations supplied by the parent

These figures are a parent-provided local inventory, based only on names and file metadata; this audit did not read data files or inspect real user folders. The native `ledger-migration-backups` tree contained 930 store folders, 1,581 `original-*.sqlite`, 1,774 `normalized-*.sqlite`, 1,029 JSON files, 1,420 SQLite sidecars, and 823 other files (1,695,595,569 logical bytes). The native `CodexTokenBarSwift` cache root contained 1,370 files, including 266 `.sqlite` files (346,480,299 logical bytes); many non-SQLite files remain unclassified. These counts support the retry-orphan concern but do not identify any file as safely deletable.

## Safe-cleanup gates and unresolved inventory

Before any cleanup, the owner must stop all relevant app versions/writers, classify the entire sidecar family, map each candidate to a source/store identity, verify the active A/B destination and complete source proof, confirm durable activation and receipts, establish that normal runtime discovery no longer reads the old source, and retain an explicit rollback copy for the chosen retention period. A retryable or missing-source batch, an interrupted candidate, a receipt mismatch, or an unclassified file blocks cleanup.

The code inventory explains known names and creation paths, but does not classify every file in the parent-provided `CodexTokenBarSwift` count or every `other` item in the ledger-backup count. Those remain preserve-only until a future app-generated ownership manifest can classify attempt UUIDs, proof references, and retirement state. No files were deleted by this audit.
