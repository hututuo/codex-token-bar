# Rust 耗时差距定位与修复

用户要求针对相同规模输入下 Rust 明显更慢的现象定位原因。本轮只处理实测热点，不恢复之前已停止的广泛对抗审查。基线为 `36ffc441a6ea79ab143d7922313f803d5bc07000`；全部数据来自保留的隔离夹具，没有修改正式数据库或安装应用。

## 已确认的两个问题

### 发布时重复全表扫描

`usage_ledger_pending_bindings.source_id` 外键指向 `pending_sources`，但子表只有事件主键，没有来源索引。`publish_schema11_pending_generation` 清空 `pending_sources` 时，每个来源的级联删除都扫描剩余关联记录。

本轮完整规模实际调用栈停在发布的 `execute_batch` 内，SQLite 反复遍历 B-tree 并读取页面。对隔离库执行只读 `EXPLAIN QUERY PLAN DELETE ... WHERE source_id=?`，关联表显示 `SCAN`，其他子表使用索引。新 Rust 回归在旧实现实际删除一个来源时，产生 **16,382 次 FullscanStep** 并失败；修后通过，其他来源的关联、来源记录和外键完整性均保持。

修复是在新建账本时创建 `usage_ledger_pending_binding_source(source_id)`，在已安装且通过版本验证的账本上幂等补齐。没有改变级联关系、发布事务或保全规则。

两次完整规模准备阶段使用逐字相同的 4,124 个输入文件，均已包含语句复用改动：

| 阶段 | 未加来源索引 | 加索引 |
| --- | ---: | ---: |
| 逐来源导入 | 161.05 秒 | 163.43 秒 |
| 统一发布 `finalize_generation` | 224.37 秒 | 32.34 秒 |

这些是实际阶段计时；两轮机器负载不完全受控，修后准备阶段与库回归有重叠。因果依据还包括同一真实删除语句的查询计划、旧实现失败及索引修后的受限扫描测试，不能把全部时间变化归因于单一改动。

### 对账循环重复准备 SQL

Rust 对每个事件重新准备相同的查询及 pending 写入；Swift 对应循环已用 `withReusedStatements`。修改仅将账本对账中的重复查询和两项 pending 写入改为 `prepare_cached`。每次仍经过 namespace 绑定、参数绑定、身份、原文和数值核验；不缓存查询结果。

同一二进制、相同 128 个原始文件（15,616 事件）的开关实验：对账阶段 **2.383 → 1.576 秒**，整个历史补全 **7.630 → 6.778 秒**。收敛到实际代码后为对账 **1.485 秒**、补全 **6.478 秒**。另有更早且机器负载较高的原始对照记录，全部保留，不从多轮中挑最低值外推全规模。

## 修后全规模结果

输入为 4,124 来源、每来源 122 事件，共 503,128 事件；另有 6,250 个旧空候选、25,000 个候选对象。使用非 `test` 的生产入口，临时诊断开关仅添加计时。

| 计时范围 | 结果 | 含义 |
| --- | ---: | --- |
| 历史字段补全 | 391.860 秒 | 解析暂存、核对、导入、发布 |
| 紧随其后的同步 | 12.903 秒 | 包括消息关联补全等生产工作 |
| 汇总 | 0.746 秒 | 最后的总量计算 |
| 上述三项合计 | **405.514 秒** | 原 Rust `backfillSeconds` 口径，600 秒预算内 |
| 20 次无变化同步 P95 | **1.256 秒** | 仍超过原定 1 秒预算 |

补全的 391.860 秒内，互不重叠的主要阶段为：并行暂存墙钟 69.821 秒、与旧事件比较 19.360 秒、导入 260.268 秒、统一发布 39.979 秒，其余为准备和清理。导入内部的逐条对账为 51.830 秒，逐来源面板聚合为 **133.514 秒**；它们已包含在导入时间里，不能再次相加。后者是剩余已测热点，本轮不同时重写聚合与发布架构。

503,128 条原始事件的 ID、数值和 SQLite 类型摘要前后完全一致，2,515,640 tokens、4,124 条补全回执正确，原始文件未变，候选保留且仍为空，MAIN 对象/商店在补全前后零增长，没有数据警告。原始 producer 的顶层 PASS 仅说明功能场景完成；`full-scale-admission.json` 明确为 **FAIL**，原因是无变化 P95，不能称整体性能验收通过。

以前的 688.820 秒结果来自较早源码，包含此前已修复的重复消息查询；这次 405.514 秒是当前源码的完整结果，不是只增加一个索引的受控速度比。Swift 的 185.203 秒只测 `synchronize`，最大写锁 105.206 秒是其中的子指标。两端原夹具数量相同但 JSONL 字节和账本结构不同，不是语言速度基准。

## 验证与证据

- 移除临时计时代码后，最终产品源码重新执行完整 Rust 库：**1,773 通过、14 项原有可选测试未运行、0 失败**，见 `rust-final-product.execution.json`。新增索引回归有实际旧实现失败、修后通过记录。
- 最终产品源码重新构建并执行非 `test` 的 16 个核心生产场景，通过原有验证器；包括 8 个中断位置、每处 3 次恢复，见 `final-core.validation.json`，耗时 11.683 秒。这是小型正确性夹具，不能与全规模补全时间比较。全规模性能不通过，单独记录。
- 所有 SQL 计时、开关和缩小夹具均撤出产品源码，保存于 scratch。最终产品改动仅账本语句复用、缺失索引及其回归。
- 首次全规模运行因进程和执行会话消失而中断，原因未确认；第二次在确认缺失索引后主动结束，未完成补全；修后第三次完整结束。均保留独立状态与现场。

证据目录：`scratch/integrated-recovery/legacy-debt-20261104/performance-gap-20261105/`。关键记录为 `pending-delete-query-plan.json`、`pending-index-before.execution.json`、`pending-index-after.execution.json`、`paired-stage-table.json`、`candidate-index-full-4124.execution.json`、`full-scale-admission.json`、`rust-final-product.execution.json`、`final-core.validation.json`。历史失败和中断现场均保留；没有将旧结果改写成新的全量发布证据。
