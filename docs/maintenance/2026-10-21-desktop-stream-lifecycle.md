# Desktop 正文流订阅恢复与测速口径

## 连接恢复

初始化成功只说明 IPC 传输可用。必须由解析器接受目标会话的 v11 快照，才能将该会话计为已核验订阅；未收到快照时显示核验中或重试中，不称为正常等待正文。

macOS 和 Windows 共用以下协议语义：

1. 初始化后声明至多四个当前关注会话的 `following=true`。
2. 收到本机、所关注会话的 v1 `thread-stream-following-status-requested` 时，向请求方定向重申订阅。
3. 收到 v0 `client-status-changed` 的新客户端上线通知时，向该客户端重申订阅；所有者断开时只结束其会话的采样，清除对应基线。
4. 收到 v1 `ipc-connection-reset` 时，结束部分采样、清除基线并重申订阅。恢复后的输出重新建立基线，不重放历史正文、不跨缺口拼接。
5. 仅对尚无有效快照的订阅，在 10、20、40、60 秒后重试，其后保持每 60 秒一次；已建立基线的安静会话不定时请求完整快照。思考和工具执行期间没有正文，不能据此认定断线。

恢复仍只发送初始化、跟随/取消跟随和否定能力发现回复，不获取所有权、不恢复/中断用户会话。用量账本及历史测速记录保持原有持久化流程。

## 测速口径核查

正文流收到文字增量及本机接收时间，再由本地分词器计算 token 数；它不是服务端逐 token 的原始采样。结算事件另行提供服务端计数，其中 output 已包含 reasoning，不能重复相加。

最近一天逐字节核对的 206 段相同正文：旧启发式为 12,191 token / 380.951 秒 = 32.00 token/s；o200k 参考分词为 16,485 / 同一时长 = 43.27 token/s。31 个无生成工具调用且只有一条正文的响应，服务端 output 减 reasoning 为 11,022，本地完整正文 o200k 为 10,852（相差约 1.5%），旧启发式为 8,086（少约 26.6%）。本补丁不修改分词设置，也不改写旧样本的计数。

CC Switch v4.0.14 的代理测速与会话导入测速是两种路径。前者使用 output / (latency − TTFT)，后者使用结算 output / 重建的整次请求时长；本机数据库记录均为会话导入，不能说它们来自代理实测。相同 17 个响应，CC 导入复算为 14,892 token / 475.107 秒 = 31.34 token/s，其中 reasoning 为 9,438；Bar 这些响应的正文 o200k 接收计数为 5,171 / 120.715 秒 = 42.84 token/s。分子、分母均不同，数字接近不表示算法相同，也不能说 CC 固定低估某个比例。
