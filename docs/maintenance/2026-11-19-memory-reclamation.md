# 2026-11-19 闲置资源回收

状态：本文记录build1028阶段，当前已被build1035替代。最终根因、后续无效实验、数据库可恢复归档和实机结果见[2026-11-20根因记录](2026-11-20-memory-root-cause.md)。

## 目标与基线

用户要求继续压低内存，尽量达到100–200MB。以本机真实数据的physical footprint验收，单看RSS或刚启动时的数值不算达到目标。

上一轮build1026后台约500MB，刷新时仍能到约800MB。主账本包含33,080个schema条目；只读加载整份结构本身已有较高开销。保守指针引用树会把SQLite原生分配误归属到Swift/AppKit对象，不能据此直接判断对象泄漏。

## 本轮改动

- 主页关闭、最小化或应用隐藏1秒后卸载内容树，保留可重新打开的轻量壳。侧栏与数据服务仍由应用runtime持有。
- 安全库复用连接在空闲5秒后关闭；与事务共用同一把锁，活动操作结束后重新计时。下次使用重新验证路由、文件身份及当前schema。
- 共享源文件缓存上限由16MiB减至4MiB，继续使用原文件失效和游标规则。
- 数据库重型连接关闭、分词器缓存到期和暂存维护结束后，节流请求系统分配器归还已释放的内存页。每次至少间隔15秒，不释放仍被借用的对象。

没有更改数据库schema、历史保留期、金额计算或用户设置的正常刷新间隔。没有通过删除历史数据降低内存。
