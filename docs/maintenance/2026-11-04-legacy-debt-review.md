## 已实现的修复

### Swift 重复 SQL 解析

`SQLiteDatabaseConnection.execute` 原先每次完整分词以识别 `VACUUM INTO`，即便该 DML 已通过所属分区验证并进入翻译／语句缓存。现将识别归到 `SQLiteStoreBinding`，对同一命名空间中已经验证的单条 DML 直接识别为非备份命令，随后执行授权仍保留。未缓存命令、DDL、上下文变化和备份继续走原检查。

原真实 XCTest 夹具、128个来源×122事件、无旧namespace：

| 指标 | 起点 | 修后 |
|---|---:|---:|
| 补全 | 8.537s | 4.404s |
| 最大写锁 | 5.599s | 2.251s |
| importing | 4.246s | 1.141s |
| 无变化20次P95 | 0.027s | 0.047s |

两次各自的原始稳定ID／数值typed摘要前后相同，解析次数等于来源数，MAIN对象和store均无增量。夹具每次生成不同路径／身份，跨运行摘要不能直接相等。采样运行另存，不能作为纯基准。512×122修后补全16.574s、最大写锁8.815s、P95 0.055s；这不能替代4124×122＋6250旧作业的压力门禁，也不代表10秒写锁问题全部解决。

### Rust 旧暂存判空合同

独立探针发现 `legacy_presence` 在清单为空时只比列名，未检查三张明细表是否有行，`table_info`还隐藏生成列；同名列的类型／约束变化及外名前缀索引／触发器也可绕过。根新增真实产品测试，改前3组全部按预期失败。

现将旧暂存准入集中到 `stage_pool/legacy.rs`：注册、目录、完整列信息和行存在性同一只读快照；空清单必须匹配已知full或partial表DDL及`table_xinfo`合同，并且三张明细表都无数据。按对象名称及所属表名检查索引／触发器。目录缓存只存结构及固定长度DDL摘要，超限仍检查当前候选，DML不缓存。正常full空作业返回false、partial空作业返回true供原恢复器处理；有清单作业继续由原多版本验证器处理，不先套当前版本字段合同。

首轮真实产品stage_pool测试11项通过。第二审查会话又用实际新模块、合成容器外壳独立复查21种输入，以及16MiB超限目录的前后顺序、外部WAL提交与超长无关DDL；该层证据不算完整产品端到端。

### Swift TEMP 归属与失败绑定

审查者发现同名TEMP表／视图可以遮蔽已绑定MAIN对象，原测试只比较改写SQL字符串，不能证明实际读到了所属主表。第二位审查者又复现两条绕过：`DROP TABLE IF EXISTS temp.facts`污染名字登记后再CREATE；或把TEMP work改名为MAIN facts。根将CREATE、DROP IF EXISTS、RENAME的归属登记统一，并保留合法TEMP改名的归属。名字仍按既有策略在连接生命周期内保留；明确指定main/temp不能改变已经登记的归属。

失败单次bind与整批SQL绑定现在恢复未执行的名字登记，避免错误语句阻止后面的合法建表。真实driver的三条顺序测试改前全部失败，修后通过；第二位审查者使用原始输入及六组批次／改名正反对照独立通过。实际行值17保持，UPDATE落到MAIN；私有未绑定迁移快照仍允许其有意使用的TEMP投影。

### 两端内部对象前缀过滤

根复查发现`name NOT LIKE 'sqlite_%'`把下划线当通配符：合法`sqliteXfacts`表会在导入与导出时遗漏，外名`sqliteXforeign`索引／触发器也会被proof及旧stage目录漏掉。真实产品Swift两项、Rust两项及stage扩展反例在修改前均失败。
