# Codex 压缩用量计账修复

分支：`codex/fix-compaction-accounting`。只修改候选源码；未替换正式应用、未写入用户生产数据库。

## 计量规则

- 仅将 `compaction_response_id` 对应的单次 `token_usage_record.usage` 作为消费；`turn_token_usage`、`thread_token_usage` 是累计快照，不能相加。
- `latest_token_usage_record` 只是最近一次请求；只有 response ID 完全匹配才可用于该次压缩。
- 通过最近请求关联识别旧 `token_count` 镜像，包括累计差值形式的镜像；保留原有普通请求身份，不重复计入压缩。
- 压缩后的零 I/O 快照只更新计数器基线，不把继承的累计值当成新消费。
- 缺失用量、缺失 response ID、无效 I/O 均不能视作真实零消费。保留显式 kind 4 未报告记录；以后取得同一请求的有效用量，可沿同一账本 ID 审计纠正。
- checkpoint 内关联窗口有界（128 条）。超过窗口后才出现的迟到关联不保证自动恢复；缺口仍保持未知，不拿累计值猜补。

## 下游链路

| 链路 | 处理 |
| --- | --- |
| 输入 / 缓存 / 输出 / 思考 | 复用原组件计量；缓存是输入子集，思考是输出子集 |
| 费用及历史价格 | 复用原三类单价：未缓存输入、缓存输入、输出；按原日期价表，不新增 Codex 订阅缓存写入费 |
| 今日 / 累计 / 周期模型费用 | 新计账事件进入原聚合；有缺口时已知值继续显示为小计 |
| 24h / 7d / 30d 图及选区 | 复用同一账本及已确认的选区消费路径；时间轴同步携带缺口信息 |
| 缓存命中统计 / 整轮排行榜 | 新事件使用真实输入和缓存字段进入原加权聚合；未知记录不参与数值和请求计数 |
| 额度反推 | 对存在缺口的可比区间不输出整期反推金额；仍保留已知选区费用 |
| 额度周期识别 / 假重置纠偏 | 已知消费可证明存在；未知压缩不得用于证明“本地没有消费” |
| 同账户消耗归因 | 有相关用量缺口时不输出肯定的本机/非本机消耗结论 |
| 实时曲线 / 正文 TPS / 排行榜上报 | 保持独立测速口径，不用累计压缩快照伪造速度；不改测速算法或上报协议 |
| 临时低命中提醒 | 不通过历史回补补弹提示；本轮未改其面向实时普通请求的观测流程 |

## 数据与升级

没有新增业务库，也没有提升 Exact 主 schema 版本。仅推进解析器及补全回执版本，沿现有后台 staging/事务发布流程重算可读取的源。旧版本回执和可识别 staging 不视为“未知新版”；旧 staging 不能被冒充为本次解析已完成。

旧数值修正必须有原始来源/请求身份证据；旧值由现有留存与 correction 审计保留。已删除或丢失源的旧账仍保留，不能为了回算清空索引。无法证明归属的改写源继续保留待核，不随意覆盖或双记。

未报告记录在源被删除/置换后也不能消失；读取留存的未报告事件，但不把已修正前的审计版本永久当作缺口。

Mac 与 Windows 使用同一语义、相同 response-ID SHA256 命名空间及现有 11 数值指纹编码的保留标记；不把两端不同的 SQLite 物理布局强行改为同一套表。

## 性能边界

按既有源断点推进，不增加服务器请求。升级后历史补全会复用后台解压流读取和 staging，属于一次性历史扫描成本，不放到启动前阻塞。关联窗口固定大小；缺口时间查询使用 accounting kind 索引，留存表增加仅覆盖 kind 4 的小型部分索引。

## 验证

最终通过状态以对应 GitHub commit 的 CI 结果及交接回复为准；未完成的测试不能当作通过。

新增回归包括真实数量级 334,108 与继承累计 17,032,149 区分、镜像先后顺序、累计差值镜像、inline fallback、缺失/错配 ID、未知到迟到用量的同批 staging 与跨次 append 修正、旧回执重算保留旧账 ID、周期缺口与三类价格公式。

本地前端全量 1,377 项已通过，TypeScript 检查通过。Swift/Rust 全量及旧公开版本产生的升级库验证在云端运行；初轮发现并修正了新测试的编译问题，后续结果见 CI。

## 本轮结论的边界

此前只读核查发现的约 1.72 亿压缩请求用量，不等于应直接追加的净额：还需排除已计镜像和继承累计的历史重复。它不能解释个人页面约 299.8 亿与本机约 127.8 亿之间的全部差距。缺失实际 usage 的请求无法据此恢复精确 Token 或金额，本轮绝不猜填。
