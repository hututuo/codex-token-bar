## 已确认的开销

本机主账本保留33,080个schema对象，包括632个`exact.swift`分区、348个`body.swift`分区。系统SQLite只读连接执行一次`SELECT count(*) FROM tb_stores`后，`SQLITE_DBSTATUS_SCHEMA_USED`为136,033,720字节，约129.7MiB；页面缓存另占8,753,152字节。这是单连接结构成本，不是所有数据行加载进内存。

全分区逐表只读核对：

- 630个exact分区没有来源与消费事件；其中420个仅有结构元数据，210个另有会话目录。
- 上述210个分区共250条目录记录，全部指向`codex-token-bar-session-management-*`临时测试目录。该来源与仓库测试夹具路径一致。
- 347个body分区仅有`speed_trend_meta`，没有样本、去重记录或聚合行。
- 有真实账目及保留历史的分区单独留存，未作清理。来源表为空不等于可以推断所有表为空。

历史原因是部分测试构造生产服务时未显式指定持久化目录，默认路径仍是用户Application Support。后来合库按已存在旧文件导入，保留了每个分区的完整物理表结构。无法仅凭当前空表证明所有其他分区都来自测试，因此本轮未按名称、大小或不活跃状态删除正式库对象。

## 内存生命周期证据

build1028一次后台快照中，实际堆分配约110MB，但默认malloc区仍保留约534MB空闲碎片。连接关闭和对象释放并不意味着系统页面已全部归还。该机同时存在活跃客户端工作；不把样本称为静止系统基线。

build1029把SQLite与Swift/UI分到独立Darwin zone。完整候选测试通过，发布二进制并发诊断通过，真实进程`vmmap`也出现`TokenBar SQLite`区。但实机仍接近1GB：长期连接与短期大schema仍共享同一区，另有默认分配区碎片。因此该版只验证了分配归属，不能算达到内存目标。

连续采样100次约640秒：主页展开15次为629.5–1024MiB、中位971.4MiB；主页关闭后85次为377.6–1024MiB、中位734.2MiB。超过1GiB时`vmmap`的G单位显示精度有限。早期采样继承了上轮场景文本，统计已按实际关闭窗口时间重新分组，修正说明单独保存在证据目录。

下一修订把SQLite分配区绑定到同步数据库操作。每块分配携带原分区身份；操作结束后，只有实际存活分配会延长分区寿命，最后一块释放时销毁整区。跨线程释放、延迟关闭、保留句柄与异常回滚仍按原生命周期发生，不提前释放活动对象。

## 源码修复

- 测试进程的默认索引、测速、用量、额度与安全库目录统一落入进程独立临时根；显式传入的夹具路径及生产目录规则保留。增加真实服务建索引后确认未写入用户Application Support的回归。
- Agent Speed每文件解析器原来同时预留九种机器的内联空间，只初始化其中一种；改成只分配实际payload的写时复制存储。原有全客户端状态、修改、重置、独立副本测试继续执行，增加内联空间上限回归。
- SQLite公开allocator接口在进程初始化前安装，过晚时保留默认行为，不调用`sqlite3_shutdown`。独立子进程回归保留一个长连接，同时反复并发创建/关闭大schema，核对操作分区回收，并验证离开scope后的指针可跨线程realloc/free。
