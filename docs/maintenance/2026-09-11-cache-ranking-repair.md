# 缓存命中排行榜恢复（2026-09-11）

## 原因与范围

本机双端旧索引有约 42.6 万条计量记录，但轮次候选为零。解析器依赖旧 event_msg user_message / agent_message；转写日志仍保留 response_item message user / assistant，却未被识别。已存在账本记录的重关联分支也没有填补缺失逻辑轮次。

## 修复策略

- 兼容旧消息和新 response_item 消息，排除 developer / tool 消息。图片用户消息可形成轮次。
- 账本关联补全只填缺失的逻辑轮次，不覆盖已有逻辑分组。
- 独立消息标记扫描器只匹配当前 generation、available 绑定中的原始字节位置，不调用 Token 计量解析器、不插入新消费。
- 完整匹配原有全部 chunk（含数量、块位置、字节数、哈希），并检查扫描前后文件元数据，才更新消息绑定与恢复续读的消息检查点。
- 分页子 Agent 使用已有 ordinal/自有 turn 证明，旧 fork 使用现有 replay 边界。不可证明的继承问题不关联到子任务。
- 每文件关联、对应会话排行重建、完成回执同事务提交；中断保留已完成部分。文件 generation 回执使之后的正常刷新跳过已完成文件。
- Swift pending 标记保证细节更新后发布 generation；Rust 同时推进 revision / dashboard_revision 使内存排行缓存失效。
- 保持索引 schema 13、计量 parser revision 不变。正式 Swift6/Rust9 升级链路继续使用原实现。
- retention writer 4→5 只调整元数据触发器：位置从 NULL 补为已知不会另复制整条数值历史；已知位置被改/清除及数值改变仍保留旧证据。兼容 writer 2/3/4。
- 不持久化问答正文，只保留位置；摘录继续按需读取。
