# 新旧目录双索引冲突：只读诊断与复现

用户截图报错：`同一业务分区存在内容不同的旧库候选；保留所有来源并拒绝切换：exact/index/...`。截图未显示版本、物理来源路径或两库内容，不能确认该用户具体差异。

## 已确认的代码问题

公开 v0.9.7 的 `relocate_legacy_index` 复制 cache 索引到 support 目录，在目标库 metadata 中写入 `release_upgrade_retention_v1`，保留原库。之后目标库还可能持续新增真实账目。

当前发现阶段枚举 support 和 cache 两个 `exact-token-index`，将同相对文件名映射到同一逻辑目标。`business_store_route::open_store_at_with_hook` 要求多个候选的 `snapshot_digest_path` 一致；该摘要包含完整 schema 和所有表行，也包括 metadata。因而正常搬迁副本也可能被拒绝。此处不是单纯比较数据库文件字节，但语义上依然过严。

上一轮恢复测试验证了迁移清单阶段、主库/回滚选择、中断和 A 初始化前后，但未覆盖真实搬迁后 support/cache 同名双库共同参与导入且证明不同的路径。

## 本地可重复证据

分支：`codex/diagnose-dual-legacy-ledgers`，仅添加诊断测试及本记录，未修改生产逻辑、打包、部署或发布。

测试 `diagnostic_relocated_legacy_pair_reproduces_conflicting_candidates`：在临时隔离目录创建真实 Exact 索引和 115 Token 记录，调用保留自旧版的搬迁实现，然后让双目录一起走发现器与真实容器导入器。

结果：两库 `SUM(event_rows.tokens)` 均为 115，复现与截图相同的中文错误；两库文件在诊断导入前后字节不变。测试 1 通过、0 失败（断言当前错误确实存在，并非修复已通过）。完整日志：`scratch/legacy-migration-hotfix/dual-legacy-repro.log`。

这证明正常旧搬迁路径足以触发该错误；不证明用户两库只有 metadata 差异，也不证明所有差异可直接忽略。

## 修复必须覆盖的范围

不能简单忽略错误、按修改时间选最新或任选一库。应先识别并验证迁移凭据、Home 身份、来源谱系，区分保留原件与已接续使用的活动账本；只差迁移元信息/可再生投影时允许接续。包含额外真实记录时需核对稳定记录身份、覆盖关系和冲突，保留两边独有的历史及 fork 后新增记录，避免重复计数。无法证明安全的冲突仍保留双方并输出具体来源/差异诊断。

验收应加入：正常搬迁后双库、仅迁移元数据不同、活动副本继续新增、旧库独有且原始会话已删除的记录、双方各有独有记录、同记录身份数值冲突，以及跨 schema 的可比较性。需要 Windows 非 cfg(test) 入口复现并验证，不能用单源恢复测试替代。

## 用户补充：升级完成后的停用与清理

用户提出升级成功后旧库应清理。落地顺序必须为：验证完整接收、持久提交输入归属及新库激活，再将原件退出发现/日常读取，最后按可验证回滚备份规则清理冗余副本。不能用删除旧源解决尚未完成的冲突，也不应将已完成导入的原件反复当作活动候选。

已开始的链路修复：`exact_sources_already_consumed` 仅在 A 已全局激活、目标确有表、全部现存来源有同分区收据时，允许日常打开跳过旧源与旧清单。未完成批次、空登记和任何未知现存来源均不走捷径；A 自身候选恢复仍在后续 open_at 中执行。针对激活前后、旧源不可读/删除、未知来源和空分区的测试 1 项通过。此项只修成功导入后的旧源角色，不代表双库首次归并或整个任务已经完成；无实际旧文件删除。

全链路审计确认还需同步解决：bootstrap 与 runtime 双入口共用对账；不同证明的来源不能调用 identical-receipt 冒充同库；复合来源必须在写 A 前持久化独立对账日志，并与完整来源证明绑定；启动激活前核验所有批次，重试不漏账、不重复。只有相关迁移已提交并可从 A 还原时才允许清理冗余原件。此分支未发布，0.9.9 公开资源不变。


## 后续候选实现（独立分支，未发布）

用户已确认本次故障发生于已安装的 0.9.9。新增 Windows 生产恢复场景重建其残留状态：Exact 已注册但未导入、A 尚无初始化标记、support/cache 两份同名数据库共同存在。

- 通用模块仍要求完整 schema/typed-row 证明一致。Exact 只为已验证搬迁来源提供独立对账规则：排除唯一的搬迁 metadata 行，或证明某份快照覆盖另一份全部保护性历史数据。不按文件时间选库，不累加两份汇总。
- 搬迁凭据兼容 Rust 整数 schema 和 native Codable 十进制字符串 schema；未知版本、浮点版本及不完整凭据不冒充已知版本。
- 覆盖规则核对 Home、schema14、事件原始数值、历史纠正/未解析信息、来源路径及子 Agent 身份、原始绑定和未来事件 ID 计数器。可变扫描/重建状态不能当作另一份独立账目相加。原始来源与完整备份始终保留。
- 原件已删除的历史也通过索引校验；双副本只发布一次，双方的输入归属分别登记，证明记录独立于业务表。
- 重试批次升级为 version2，冻结每个输入路径、备份路径、完整证明。发现器漏掉已移走原件时仍遍历未完成批次；只读备份证明通过后恢复，不创建新的旧原件。备份损坏而相同证明的原件仍在时，先保留坏备份再重建；不能用不同证明的原件顶替。
- 重试发现原件变化时，先证明新增版本覆盖冻结历史，再允许替换未激活分区；截断/改写不能抹掉第一次已导入的独有记录。旧尝试的绑定快照凭据另存于 metadata，不随重试日志覆盖而失去来源。
- 正式激活后，原件的角色为冻结恢复材料，正常统计不再将其当作活动写入器。其他 A 分区的已提交新增记录在恢复中保持。
- Mac 原样输入重试复用经完整证明的 original/normalized 对；每个完成尝试新增独立 attempt-UUID.json 凭据，避免最新 receipt.json 覆盖后丢失旧副本归属。

本候选仍不对任意分歧账目做猜测性 union：两个独立计数器增量直接相加会重复计费。不能证明覆盖的真正分歧、未知 schema、损坏且无可信副本等状态保留全部现场并阻止替换，不把它们伪装为空库或正常升级。不同 schema 的任意双库历史归并不在本轮已验证范围内。

## 已确认的跨版本双副本路径（11 月 1 日追加）

公开 v0.9.2/v0.9.3 的 CURRENT_SCHEMA_VERSION 为 13，v0.9.4–v0.9.7 为 14。搬迁器在支持目录目标存在时直接返回，不再打开旧缓存索引。因此正常从 v0.9.3 升级也会留下 support14/cache13；旧搬迁凭据的 targetSchema 仍可能保留 13。只测14/14不足以放行此用户群。

13→14 的表示层升级仅新增 source_representations 表及表示层 metadata，不修改既有事件。另一个已知变化为 ledger revision1→2：新增 canonical 数字投影/证书对象，保留物理事件及绑定。新候选在只读比较中明确接受这两个已知的附加变化，同时要求当前副本确有已知 v2 对象，继续逐项比较旧事件、绑定、纠正及保留证据；不将任意不同 schema 当作相同数据。这样无需创建更多临时 SQLite，也不读取用户原会话。

除临时库的已知升级逆向回归外，Windows 专项新增真正的公开 v0.9.3 产库器（固定提交 ba4c59060c240af703e42d288c303a56cb0259e3）。它在隔离目录使用同一份 v0.9.7 合成 Home/原始文件生成 schema13，独立记录原始证明，生产探针验证13/14正常启动和已初始化后再发现两条路径。它不是将当前库随意改版本号来替代旧版产物。最终验证回执需覆盖这些新增场景；35fcfe01 的两个绿色工作流是加入该场景之前的基线。


升级专项进一步补齐真实接续：schema13 由公开 v0.9.3 生成后，schema14 配对副本再由公开 v0.9.7 对这份旧库实际打开/升级/同步生成，而非仅拿两个独立新建库比较。共同的合成原始记录包含用户消息和工具调用/返回，以覆盖轮次及原始位置绑定。两份旧输入的产物与两端发布代码提交均登记完整散列；新候选只导入合成副本，原始旧产物再次校验未变。
