# 聚合查询修复后的下一组热点

本轮针对 `8ef7bc61` 继续定位性能，未更改产品行为。使用原生产入口、4,124 个来源、503,128 条事件及 6,250 个旧空候选，临时添加粗粒度函数计时，并在回填和日常刷新阶段分别采样调用栈 3 秒。所有临时探针已撤出，产品源码逐字恢复到 `8ef7bc61`；本记录不表示下面两项候选优化已经实现。

## 优先处理日常刷新的两项重复工作

20 次无变化同步的平均总耗时为 1.793 秒。以下三项是总耗时内的不同部分，不能再与总耗时相加：

| 操作 | 平均 | 中位数 | 占平均同步耗时 |
| --- | ---: | ---: | ---: |
| 记录迁移成功状态 | 1.131 秒 | 0.801 秒 | 63.1% |
| 确保面板聚合已准备 | 0.380 秒 | 0.352 秒 | 21.2% |
| 来源文件变化检查 | 0.246 秒 | 见原始报告 | 13.7% |

### 1. 为查迁移凭据反复打开主库

确定的调用链为：

`sync_with_scan_plan_mode_once → record_successful_migration_retention → active_schema11_paths → preserves_legacy_exact_migration → open_ready_container → Container::open_existing → validate_version_on → sqlite3ReadSchema`。

新建或没有 `release_upgrade_retention_v1` 成功回执的索引，每次成功同步都会进入这条路径。即使最终没有迁移标记需要更新，也先重新打开主库并加载约 2.5 万个 schema 对象，才查询 `tb_container_meta` 中的一项凭据。旧库完成迁移且已有成功回执时会提前返回，所以不能说所有用户每次刷新都必然付出同样成本。

实际调用栈中 871 个样本位于迁移记录路径，834 个落在新连接的 schema 加载链上。独立的只读机制实验使用同一 SQLite 3.50.2、同一个已保留夹具、同一 root-version 查询：新连接首次查询为 1.125、0.560、0.520、0.525 秒；复用连接为 0.023～0.083 毫秒。该实验说明重新打开连接的代价，不是完整刷新提速比例。

建议修复：让已有且经过校验的主库连接承担迁移保留凭据查询，保留运行状态、初始化标记、物理文件身份、root 版本、Exact owner 和凭据版本/逻辑路径校验。沿用已实现的 held-connection 校验思路，不缓存“没有凭据”这一结论，也不因缺少成功回执就跳过后续出现的合法迁移标记。不能为了提速删除旧凭据、压平候选目录或改变恢复路径选择。

具体入口：`exact_usage_index.rs` 的 `record_successful_migration_retention` / `active_schema11_paths`，以及 `business_store_route.rs` 的 `preserves_legacy_exact_migration`。

### 2. 聚合已正确，仍为进度显示重新数全部事件

`ensure_dashboard_aggregates` 已验证当前 aggregate schema、generation、pricing revision 和投影签名。但它的快速返回还要求展示层的 `dashboard_aggregate_published_generation` 和 settled-through 标记同步更新；标记暂时落后时，会调用 `published_event_count`，逐来源统计全部事件，并进入一次实际不需要重建聚合的写事务。

本夹具在历史补全后先运行 20 次 `index.sync`，最后才生成一次 dashboard。期间展示发布标记尚未追上，所以这项成本每轮重复。实际采样中 `ensure_dashboard_aggregates` 的 323 个样本里有 311 个在 `published_event_count`。这个状态也可能出现在真实的索引同步与 dashboard 发布之间，但不能把夹具的全部重复次数直接当成 UI 正常刷新必然发生的次数。

建议修复：数值聚合已经匹配当前版本时，跳过迁移进度计数和无实质修改的事务；展示发布标记继续由原发布者更新。不要把“统计已准备好”伪装成“界面结果已发布”，也不要取消投影截断自检或 Summary→Full 补齐。计数只在真正重建时用于进度。

### 3. 文件扫描暂列其后

来源检查约 0.246 秒，其中目录遍历和逐文件校验是主要部分。路径会重复检查 plain/zst 选择、规范化边界、元数据和打开后的物理身份。它有可复用的工作，但也承载文件替换、压缩切换和符号链接边界的正确性，因此当前收益/风险优先级低于前两项。不能直接改成只相信 mtime、只相信 watcher 或跳过第二次身份核对。

统计完整性签名和旧版本候选查询的只读 SQL 复现仅为毫秒到几十毫秒；它们不是本轮秒级日常刷新的主要原因。保留负面结果，避免优化错误目标。

## 回填剩余成本

以下来自同一次诊断运行的回填窗口，包含紧随其后的 sync/summary 工作。`import_staged_full_rebuild` 总计 171.206 秒，内部账本对账和单文件聚合已包含在它里面：

| 工作 | 累计时间 | 关系 |
| --- | ---: | --- |
| 解析、暂存和等待批次完成 | 86.599 秒 | 独立阶段的墙钟时间，含工作线程等待 |
| 逐来源导入 | 171.206 秒 | 下两行是其子项 |
| 其中：逐条账本对账 | 54.045 秒 | 导入内部 |
| 其中：单文件面板聚合 | 30.796 秒 | 导入内部，范围更新为其中 11.129 秒 |
| 与旧事件比较 | 21.780 秒 | 导入前核对 |
| 发布与收尾 | 49.784 秒 | 两次 finalize 调用的累计值 |

范围聚合已从之前记录的 133.514 秒降到本轮约 30.8 秒，说明下一步不应继续只盯聚合 SQL。暂存阶段约 86.6 秒是更大的剩余块；3 秒调用栈在一个暂存批次中多数时间显示主线程等待工作线程，因此不能把该样本直接归因为解析器 CPU。下一次回填调查需要继续拆分工作线程的解析、编码/校验和阶段池写入时间，再决定是否调整批次。现有导入代码已复用同一份被验证的不可变暂存快照；不能把已修复的二次恢复问题重新当作新发现。
