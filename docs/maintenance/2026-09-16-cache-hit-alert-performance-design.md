# 缓存命中提醒：实时性、功耗与原链路复用方案

## 结论

缓存命中提醒应作为实时速率链路上的轻量派生信号实现。双端继续按现有游标读取新增 JSONL，只在已经解析出的 `token_count` 上提取 `input_tokens` 与 `cached_input_tokens`，计算本次请求的缓存命中率并驱动提醒状态机。

采用该方案后：

- 原生检测目标为完整记录落盘后约 `1 s`；跨平台还可能叠加最多一个发布周期。轮询周期不是端到端延迟保证，需要包含读取排队和 UI 发布进行验收。
- 不增加常驻定时器，不枚举历史会话，不启动精确索引同步，也不重新聚合 7d、金额、排行或周期历史。
- 实测额外字段提取和比例计算约 `0.00025 ms/条`。按本机样本平均约 `5 条/小时`，该微测只覆盖字段计算，不能证明整个提醒功能的 CPU 与电池开销。
- 提醒只表达最近请求的即时状态；历史图表、金额和正式命中率仍由精确统计链路负责。

## 现有链路

### Swift

`LiveRateMonitor` 已有自适应刷新：活动阶段每 `250 ms`，空闲阶段每 `1 s`；日志目录事件可以在 `20 ms` 后提前唤醒。实际读取通过数据库 ID 和 JSONL 字节 offset 增量推进，不从文件开头重复读取。

`LiveRateMonitor+Rollout` 已经把新增 JSONL 行解析成对象。当前遇到 `event_msg/token_count` 后直接忽略，因此实现提醒只需在这一分支取出两个现成字段，并发布轻量缓存样本。无需调用 `CodexUsageAnalyzer` 的完整历史分析。

### Tauri / Rust

`LiveRateMonitorService` 同样采用活动 `250 ms`、空闲 `1 s` 的刷新周期，并根据文件签名和 offset 读取新增行。Rust 当前已经在 `token_count` 分支读取 `last_token_usage.reasoning_output_tokens`，所以缓存提醒可以在同一个已经完成的 `serde_json` 解析结果上继续读取输入与缓存输入字段。

原生流活动时每 `250 ms` 可更新内部状态；WebView 事件已有 `1 s` 上限，提醒实现应保留该上限，避免因为响应流频繁写入而增加渲染和 IPC 负担。

## 实现设计

### 数据流

```text
现有日志/JSONL 变化
  -> 现有 LiveRateMonitor 增量读取
  -> 现有 JSON 解析
  -> 新增 CacheUsageSample
  -> 轻量提醒状态机
  -> 原生提醒状态 / WebView 事件

原有精确刷新
  -> 索引同步与正式聚合
  -> 历史图表、金额、排行、周期数据
```

实时提醒链路和精确统计链路共享原始字段含义，但互不触发。实时样本不能写入正式账本，也不能把缺失字段写成 `0%`。

### 建议的数据对象

`CacheUsageSample` 至少包含：

- source identity；
- thread / session identity；
- turn identity 或可稳定去重的记录 identity；
- timestamp；
- model（能从当前 turn context 确定时）；
- input tokens；
- cached input tokens；
- hit rate；
- provenance：`last_token_usage` 或 `total_token_usage`；
- validity：字段缺失、输入为零、数字非法时标记 unknown。

实时提醒优先使用 `last_token_usage`，它代表本次请求。只有累计值而没有可信差分时，保持 unknown，不用累计命中率冒充本次命中率。

### 提醒状态机

按用户明确要求，单次可信请求命中偏低就立即进入提醒状态，不等待第二次，也不设置阻止后续异常的冷却窗口。

1. 输入 Token 至少 20,000、缓存命中率低于 30%、记录在两分钟内且有效时提醒。
2. 正常命中、未知或小样本清除本会话当前异常；后续新的低命中请求立即提醒。
3. 来源与会话隔离；重复请求去重，重写和旧历史不重放。
4. 用户主动收起后，同一请求不重复弹开；后续新请求仍可立即提醒（2026-09-26 三级提醒补全后按请求标识去重）。
5. 未知字段显示“等待缓存数据”，不伪装为 0%。

双端共用相同默认阈值与测试向量。

## 性能与功耗预算

实现必须满足以下预算：

- 空闲时新增定时器：`0`。
- 空闲时新增周期性文件枚举：`0`。
- 单次提醒触发的历史索引同步：`0`。
- 单次提醒触发的完整 dashboard aggregate：`0`。
- 单条样本只允许常数级字段读取、去重和状态判断。
- Native 到 WebView 的缓存状态发布不得快于现有 `1 s` 节流；系统通知只在状态跨越提醒边界时发送。
- 状态持久化只保存必要的去重信息；不复制原始 JSONL，不建立第二套历史明细索引。
- watcher 丢事件时继续依靠现有 `1 s` 空闲兜底；不得为了提醒另设高频轮询。

按当前样本平均 `5 条/小时` 计算，纯字段提取每小时新增 CPU 时间约 `0.00125 ms`。即使把分钟峰值 `8 条` 假设为整小时持续，纯字段提取每小时也只有约 `0.12 ms`。真正相对更大的成本会来自界面发布和系统通知，因此必须使用状态变化发布与重复请求去重，而不是每条样本都重绘、通知。

字段微测不能推出新增 CPU 百分比或电池影响。性能结论待整包 A/B；优先检查新增唤醒、读取字节、CPU time、IPC 和持久化写入，再报告可测得的差值及噪声范围。

## 兼容性与安全边界

- 兼容上一正式 release 的既有索引和设置；提醒功能不要求索引 schema 升级。
- 对 OpenAI 新旧 JSONL 格式继续使用现有解析兼容层，只消费已经验证为非负整数的字段。
- 历史记录被重写、迁移或压缩时，不回放旧样本产生提醒；首次绑定从文件尾部或已有实时游标继续。
- 文件截断、inode 变化、边界签名变化和 Codex Home 切换复用现有重置逻辑。
- 精确统计仍是金额、周期、历史图表和缓存排行的唯一权威来源；实时提醒不改变任何会计口径。
- 提醒关闭时不发布提醒事件，解析链路仍可按实时速率功能的现有开关运行；如果实时速率整体关闭，提醒功能是否独立启用需要在设置模型中明确，不能暗中恢复高频监控。

## 2026-09-16 复核后的落地方案

### 源码复核与接入前置条件

本次复核 HEAD 仍为 `81ffdce2`。Swift 的 `LiveRateMonitor+Rollout.swift` 在 token_count 分支返回空事件；Rust 的 `core/live_rate/rollout.rs` 只取 reasoning，并在 reasoning 为零时提前返回。缓存样本必须在该提前返回之前提取，否则只有输入、没有 reasoning 的请求会漏掉。

当前工作树未找到 `UsageAdvice` / `usage_advice` 或低缓存提醒策略的实现。此前任务有提醒功能的记录，不能当作本分支已经具备该能力。实施第一步检查相关提交与工作树，定位现有策略和设置后集成；不得凭旧记录新建第二套提醒系统。

Swift 当前解析器缺少 ID 时使用 UUID。该 ID 不能充当缓存样本去重键；本批次行号也不稳定。需由读取层传入文件代次与绝对字节位置。解析器返回并列的 `metricEvents` 和 `cacheSamples`，保持原有速率事件含义，不能把输入 Token 当输出速率事件送入累计器。

### 样本可靠性与去重

- 必須同时存在 input 和 cached input，均为非负整数，且 `0 ≤ cached ≤ input`、input 大于零；非法值为 unknown，不截断成可信比例。Swift 需拒绝布尔值及小数被 NSNumber 转成整数。
- 第一版仅采用可靠的 last_token_usage。累计值用于可选的一致性检查，不实现累计差分回退，以免重写和归零制造假请求。
- 传输去重使用 source + session + file generation + absolute offset。若存在可信 request/response ID，再做请求级去重；不能只按 turn 去重，因为一轮可有多次请求。
- 同一请求可能被重复上报到不同位置：无请求 ID 时，结合已有累计用量水位判断重复；只有相同 last 用量不能判重复，因为两个真实请求可以恰好用量相同。无法确认独立性的记录可展示，但不作为新的独立请求重复提醒。
- 保留事件时间和本机接收时间：前者做新鲜度筛选，后者用于监控中断检测。缺失时间、明显未来时间、重放旧样本不通知。
- 不为获取 model、title 或 request ID 额外查库；缺失模型时标明未知，不能沿用其他会话的模型。

### 策略建议与展示含义

采用 input ≥ 20,000、命中率 < 30%、记录新鲜度 ≤ 2 分钟。满足条件的第一条可信新请求立即提醒，正常后再次异常也立即提醒。

仅展示应用内提示；多个 Agent 同时异常时合并展示异常会话数。文案为“最近请求缓存命中率”和“本次请求缓存命中偏低”。需要等待本次 token_count 落盘并经过既有发布节流，但不等待下一次请求。这不说明上游缓存失效的具体原因。

### 监控生命周期与发布

提醒复用同一个监控服务，通过消费需求决定是否运行：速率或提醒任意开启即可保持既有服务；两者都关闭则不为提醒保活。接入前核对当前隐藏窗口、菜单栏、暂停、切换数据源时的服务生命周期，不能只在可见组件里启动，否则隐藏界面后会漏提醒。

同一批读取先在后台依次处理全部样本，再合并发布最终展示状态和本批新提醒；不能只保留批次最后一个样本后才判断异常。WebView 仍复用现有发布节流，且 snapshot 相等性/变更检测必须包含缓存状态，避免速率未变时吞掉提醒更新。过期判定利用既有 tick 或下一次交互，不新建定时器。

状态仅保存当前监控集合中的小记录，并设有界容量和淘汰规则。重启默认不回放通知；优先借助既有启动水位隔离历史。提醒状态只保留在内存，不逐样本写盘，不增加定时落盘。

### 分步实现与验收

1. 定位既有提醒提交、设置和消费生命周期，确认能够接入本分支；写出实际文件改动清单。

- 沿用现有读取游标做传输去重，不复制日志、不创建缓存明细库、不修改任何索引 schema 或金额口径。Rust 为防同 inode 重写增加游标附近最多 256 字节的边界比对，仅在绑定或文件变化时读取；一次变化通常最多额外读取 512 字节，无新增空闲周期读盘。
- 文件重写/替换时旧内容不会产生提醒；应用重启从原实时尾游标建立观察。跨平台还修正了 lossy UTF-8 解码后以字符字节长度推进原文件 offset 的问题，现在一律使用原始字节位置。
- 缓存状态参与 Swift 快照变化判断，并随跨平台现有事件传输；即使输出速率不变也会更新。快照复用时仍剔除过期提醒。
