## 目标

对 Codex Token Bar 的 Swift/macOS 与 Tauri/Windows 两条产品线进行全项目人工审查、历史遗留问题考古、双端目标态对齐和真实 UI 检查。自动工具只作为补盲信号，不作为人工覆盖或完成标准。审查结束后，为所有确认问题建立可复现证据和分批 TDD 修复计划，持续修复并复审，直到核心业务错误和核心技术债收敛。

## 核心原则

1. 人工审查决定覆盖范围。每个生产模块都必须出现在覆盖账本中，工具没有报告不代表模块没有问题。
2. 首轮人工审查保持盲态。审查者不接收旧问题清单和自动工具结果，只接收产品边界、只读要求和统一报告格式。
3. 工具结果单独运行。人工首轮报告封存后，再调查工具额外指出的代码点，避免锚定偏差。
4. 目标态优先于机械 parity。每个 Swift/Tauri 差异必须判断为 Swift 正确、Tauri 正确、两边共同缺陷或合理平台差异。
5. 审查与修复分阶段。发现阶段不顺手改代码；确认问题先写最小复现，再进入独立修复批次。
6. 核心链路双人复审。用量、额度、实时速率、数据源切换、未读和 Provider 写入链路至少由两个独立审查者检查。
7. Worker 报告不是验收。Commander 必须阅读关键源码、测试设计和风险路径；所有 P0/P1 独立复现，P2 抽样复核。
8. 两条运行线互不管理。Swift 任务只关闭并打开 Swift 构建；Tauri 任务只管理 Tauri 构建，Windows 运行由 Windows/Tauri 线负责。

## 审查组织

### 首轮人工审查

- Swift 开放式业务审查。
- Tauri 开放式业务审查。
- 历史债与重复修复考古。
- 测试质量、异步架构与可维护性审查。

首轮 prompt 不给固定文件清单。每名审查者必须报告实际探索范围、调用链、未覆盖区域和非预设发现。

### 辅助工具审查

- Swift：SwiftLint、Periphery、JSCpd、覆盖率。
- Tauri：TypeScript build、Clippy、Cargo Machete、Knip、Biome、JSCpd、覆盖率。
- 核心纯逻辑：定向 mutation 候选和小范围 mutation 运行。

工具输出必须区分确认问题、待验证线索、配置噪声和纯格式问题。工具输出不计入人工覆盖率。

### 收口审查

- 根据生产文件清单生成覆盖账本，补派首轮遗漏模块。
- 将两边报告汇总为功能目标态矩阵。
- 用同一 fixture 比较 Swift/Tauri 输出。
- 打开真实 App 完成 UI 状态矩阵和截图证据。
- Commander 复现高风险问题并裁决冲突结论。

## 证据标准

正式问题必须包含：

- 唯一 ID、平台、模块和严重度 `P0/P1/P2/P3`。
- 状态 `confirmed/suspected/product-decision/tool-noise/rejected`。
- 用户影响、触发条件、文件与行号、调用链。
- 可重复的测试、fixture、运行日志或 UI 证据。
- 现有测试为什么没有阻止问题。
- 建议目标态、修复风险和需要补充的回归测试。

没有复现证据的问题保留为 suspected，不得包装成已确认修复项。

## 修复策略

确认问题按以下顺序进入独立批次：

1. 数据损坏、错误写入、启动失败和明显错误数据。
2. 用量、额度、实时速率等核心计算链路。
3. 数据源、缓存、并发、旧结果发布和恢复行为。
4. 双端不一致和 UI/交互问题。
5. 核心技术债、测试结构和可观测性。
6. 死代码、重复和低风险维护债。

每个批次先提交红测或确定性复现，再做最小生产修复。核心模块的行为保持和缓存版本变化必须显式说明。修复后执行任务级评审、跨模块评审和最终全分支评审。

## 完成标准

- 所有生产模块至少一次人工审查，核心链路至少两次独立审查。
- 所有自动工具发现均已分类，没有遗留的未读原始输出。
- 所有确认 P0/P1 和核心 P2 已修复并通过回归验证。
- Swift/Tauri 功能矩阵没有无法解释的差异。
- UI 状态矩阵没有确认的布局跳动、遮挡、截断或错误状态优先级。
- Swift、Node、Rust 全量测试通过；真实 macOS Swift、Tauri macOS 和 Tauri Windows smoke 通过。
- 未修问题有明确技术或产品理由、风险和后续入口，不能只写“以后再看”。
