## 缓存优先与统计连续性

- Swift 先走 root-only lastGood，Tauri 先调用 cache-only 启动读取；首屏可显示“上次统计 · 正在更新”，随后后台 single-flight 迁移、校验和增量刷新。
- 未完成当前验证的 lastGood 只用于展示数字和图表，不提升为 attribution 或用户文件写操作的安全凭据。后台失败时继续保留 lastGood，并返回结构化 `repairRequired`。
- 两端 exact fingerprint 统一为 `版本字节 + 11 个 unsigned LEB128` 的可逆 BLOB。它是精确编码，不是概率哈希；模型、reasoning 等字段差异仍能精确区分。
- 统计链路只依据规范化路径、session ID、大小、mtime、首尾 probe、4 MiB chunk hash、parser checkpoint、resume offset 和已提交前缀。device ID、inode/File ID、卷序列号、Codex Home physical identity 和 ctime 不参与统计命中、增量或缓存隔离。

文件分类保持数据事实优先：

- 路径、大小、mtime 相同：`unchanged`，不读 JSONL 正文。
- 文件变大：验证 checkpoint、旧尾块和轮换审计块后，只解析新增后缀。
- 大小相同但 mtime 改变：先比较轻量 probe，再以固定 64 KiB 缓冲流式复核该文件已有 4 MiB chunks；内容一致时不跑 JSONL parser。
- 前缀或 chunk 不一致、文件截断：只重建该文件。
- 新文件：正常首次解析。
- 缺失文件：只有完整枚举成功后，才随新 generation 原子发布单文件墓碑。
- 路径下文件对象被替换但内容完全一致：视为同一份认可数据。

扫描期间继续从已打开句柄读取。若文件继续追加，只提交扫描起点前已验证的前缀，新后缀留到下一轮；发布前复核失败只废弃本轮未发布结果。

## Schema 11 存储与性能

Swift 保留原有稳定 `source_id`、events、chunks、checkpoint、aggregate 和 attribution 体系。schema 6/7 候选迁移转换 fingerprint 和相关绑定，不遍历 JSONL。

Tauri schema 11 将路径和 session ID 集中到 `sources`；events、fingerprints、chunks、enrichment、file aggregates 和 turn candidates 只引用稳定整数 `source_id`。当前发布数据与 building 变化通过 current/pending overlay 表达，验证完成后由单写者事务合并并更新 `published_generation`，append 不再复制该文件全部旧 events/fingerprints/chunks/aggregates。旧 schema 9/10 中同一路径残留的历史 generation 物理副本会压缩为最新 published 逻辑态；`published_files`、`published_events` 与统计总量必须保持一致。

Tauri 所有轻文件重建都进入最多 4 worker 的解析池，不再以 4 MiB 为串行分界；主库仍只有一个 writer。ready artifact 同时受数量和 512 MiB 总字节门禁限制，单个大于等于 512 MiB 的文件继续走 heavy lane。Swift 保留原有 2/3/4 worker 自适应和 heavy lane。完整目录枚举仍负责 tombstone，只是移出首屏关键路径。

`session_metadata` 按 thread ID / `updated_at` 增量 upsert，只有完整读取成功后才移除明确消失项。正式 title 原样保留；只有 first-message/preview 回退文本执行有界展示裁剪。

## 候选迁移与非破坏恢复

双端都在相同缓存目录使用受管候选库、迁移 manifest 和 rollback artifact：

1. 旧活动库只读；迁移前检查活动 DB、WAL、候选预估和额外 512 MiB 安全余量。
2. 候选直接复制 published、building、checkpoint、probe、4 MiB chunks、aggregates、attribution、catalog 和可证明的 staging 状态。
3. 候选通过逻辑行数、event/fingerprint digest、aggregate 总量、checkpoint、generation lineage、`foreign_key_check`、`quick_check` 和 parser-zero 对账。
4. 关闭连接并 fsync 候选和目录后，原子切换；schema 11 重新打开并再次校验。
5. 旧库只在 schema 11 成功打开并完成一次 no-op/append refresh 后退役。失败或崩溃会保留活动库、候选、manifest、rollback 和 staging，供下次继续或报告人工修复。

fingerprint 对账按 `(generation, path)`/`source_id` 分组，把旧 88-byte 编码先转换为 canonical LEB128，并在每个 source 内按 canonical bytes 排序后计算 digest。这样验证的是完全相同的 fingerprint 多重集合，不会因旧 little-endian BLOB 与新 LEB128 的 SQL 排序不同而误报；内存只随单个 source 的 fingerprint 数量增长。

identity 漂移、未知 schema、迁移失败、`quick_check` 失败、DB/WAL 收据失配、权限/磁盘/锁/I/O 失败、枚举不完整、staging 恢复失败以及内容 probe/checkpoint 不一致，都只能返回 lastGood 或 `repairRequired`，不能删除活动库、整表清空或清理缓存 namespace。会话删除、Provider Sync、项目移动等用户文件写操作继续使用原有安全保护，不属于本次解耦范围。

## 2026-09-06：准备阶段去重与会计迁移衔接

本节是后续更新：结构候选契约仍为 schema 11；当前活动 writer 已由独立会计转换推进到 schema 12（参见 `docs/handoffs/accounting-standard-api-20260906.md`）。上文 schema/cache 版本表和耗时是此前阶段的验收记录。

本次现场 Tauri 首轮后台 owner 为 74.599 秒，其中 open/preparation 59.273 秒、sync 10.364 秒、dashboard 构造 2.130 秒。随后 open 仅 14–22 毫秒，另一次额度触发刷新总耗时 12.087 秒。旧日志没有进一步拆分 open 内部耗时，因此不能把 59 秒全部归为复制、迁移或锁等待。启动初始请求已由后台 single-flight 合并；下一个五分钟额度观测边界仍可能发起后续刷新。

### 本次修改

- 在同一次持有操作锁的打开流程内传递 `Schema11ValidatedStorage`。它只由成功校验产生，不从 manifest 反序列化为可信凭据；DB/WAL 的大小、mtime 和 schema/revision/generation 元数据匹配时，候选重命名与后续打开复用该次校验。
- `Validated` / `Switching` 跨进程恢复重新验证候选；源文件或候选收据变化拒绝旧证明。切换前再次核对活动库收据，所有错误保留已有恢复材料。
- 连续迁移只对旧库和候选库各跑一次 `quick_check`，由 5 次减少到 2 次。候选外键检查统一放在压实之后、切换之前；完整对账时的 canonical fingerprint 解码同时验证编码，避免再单独遍历一遍指纹。
- 结构候选对账成功后的 facts/digest 供紧接的会计转换使用。若连接内已有其他写入或 lineage 不同，回到重新计算；跨进程不得凭一个旧内存结果直接复用。
- 独立 schema 11→12、没有待完成结构 manifest 的升级，不再为不存在的候选比较构造整套结构摘要。`accounting_structural_receipt` 只服务仍在管理中的结构切换；已有完整性检查和会计事务继续执行。
- 单纯的会计版本升级不再重新初始化结构/会话目录并写入相同标记。会计转换在同一事务中验证并发布刚重建的聚合版本，防止首次完整读取再次复制或重建同一批派生统计。
- 新增 `exact_prepare stage=... elapsed_ms=... status=...`，拆分进程锁、文件锁、候选准备、兼容性读取、完整性检查、结构与 provenance、facts/digest、候选复制/压实、会计行转换、聚合、归因台账及提交。字段不包含原始会话内容。

候选、manifest、rollback、lastGood 的恢复机制和既有成功后退役条件保持；没有增加旁路数据库，没有删除或重建真实活动索引，没有更改额度实时显示或历史过滤规则。
